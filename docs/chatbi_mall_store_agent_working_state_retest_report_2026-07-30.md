# ChatBI“商城店铺主题”Agent 工作状态改造后真实测试报告

## 1. 测试结论

本轮基于当前工作区代码，使用真实 Chat Agent、真实模型、真实语义层和真实商城 MySQL 数据重新执行了 10 个不同分析层面的问题。所有筛选对象均使用具体业务 ID；出现结构化澄清时，每个选项都通过独立 Chat、Record 和 Agent Run 实际选择。

正式测试共执行 `18` 个 Agent Run：

- 10 个主问题 Run。
- Q4“商品库存 Top5”的 3 个问题理解澄清分支。
- Q10“客户数”的 5 个指标澄清分支。

按业务问题是否得到正确答案判断，10 个场景中通过 `6/10`：

- 通过：Q1、Q2、Q6、Q7、Q9、Q10。
- 失败：Q3、Q4、Q5、Q8。

本轮最重要的正向结果：

1. **维度值不参与语义资产检索的修改仍然有效。**
   - 共有 `13` 个 Run 进入语义检索。
   - 所有检索计划均只包含 `metric:*` 和 `dimension:*` 子查询。
   - `value:*` 子查询数量为 `0`。
   - 店铺 ID、商品 ID、订单号均作为字面筛选值保留。

2. **多值维度表达已经修复。**
   - Q5 正确识别店铺值为数组 `['100011', '100012']`。
   - 编译参数使用 `operator: "in"`。
   - SQL 正确生成 `stall_id in ('100011', '100012')`。

3. **没有再出现执行 SQL 前预算耗尽。**
   - 正式测试中预算错误为 `0`。
   - Q5 虽然消耗 10 步、`90913` Token，但仍在预算内完成 SQL 执行和最终收口。
   - 编译成功后，可信工作状态能够保留 `execute_sql → finish` 的完成路径。

4. **Q10 的 5 个客户数指标选项全部成功。**
   - Asset ID `272 / 273 / 274 / 313 / 310` 均在独立 Run 中实际选择。
   - 五个分支均完成语义编译、SQL 执行和回答。

仍然存在的主要问题：

1. Q3、Q8 的完整中文日期范围 `2026年6月1日至2026年6月30日` 仍被归一化为 `unsupported`。
2. Q4 仍无法确定排名问题中的商品 ID 是分组和展示维度，并错误地把指标名中的“当前”判为时间冲突。
3. Q5 虽然多值筛选已经正确，但比较查询没有按店铺分组，只返回两个店铺的 GMV 合计，无法判断哪个更高。
4. 模型仍会选择重复检索、无效编译或当前状态不允许的工具。服务端守卫能够拒绝这些动作，但模型规划步骤和 Token 已经消耗。
5. 部分需要澄清的场景中，模型把澄清 JSON 或选项写进普通文本，没有真正调用 `clarify` 或建立结构化澄清，随后被“无查询结果禁止直接回答”守卫拦截。

## 5. 通过场景的 SQL 和结果

### 5.1 Q1：单指标

语义编译计划使用：

```json
{
  "metric_asset_ids": [274],
  "dimension_asset_ids": [],
  "filters": [
    {"asset_id": 278, "operator": "=", "value": "100011"},
    {
      "asset_id": 276,
      "operator": "=",
      "value": {
        "kind": "absolute_range",
        "start": "2026-06-30",
        "end_exclusive": "2026-07-01",
        "timezone": "Asia/Shanghai"
      }
    }
  ]
}
```

SQL：

```sql
select sum(fct_stall_order_daily.order_customer_cnt_total)
       as order_customer_cnt_total
from fct_stall_order_daily fct_stall_order_daily
where fct_stall_order_daily.stall_id = '100011'
  and fct_stall_order_daily.stat_date >= '2026-06-30'
  and fct_stall_order_daily.stat_date < '2026-07-01'
limit 100
```

结果：`3`。

需要注意：第一次编译时模型传入 `order_by: null`，被参数校验以 `invalid_tool_args` 拒绝；第二次改为 `order_by: []` 后成功。因此 Q1 业务结果正确，但仍包含一次无效编译。

### 5.2 Q2：同模型多指标

指标 Asset ID：`269 / 270 / 271`。

结果：

```json
{
  "gmv_sale": 8364.36,
  "gmv_booking": 0.0,
```

### 5.3 Q6：订单明细兜底路径

问题理解正确保留：

- 店铺 ID：`100011`。
- 未发订单号：`USO202606300001`。
- 日期：`2026-06-30`。

但“是否超时”仍被放入 `metric_mentions`，而语义层中它是 Dimension Asset `290`。语义路径没有直接完成，Agent 使用：

```text
search_semantic_assets
→ get_dataset_schema
→ get_sql_examples
→ validate_sql
→ execute_sql
→ finish
```

最终 SQL：

```sql
SELECT
    order_amount AS 订单金额,
    unshipped_qty AS 未发件数,
    is_overtime AS 是否超时
FROM snap_unshipped_order
WHERE snapshot_date = '2026-06-30'
  AND stall_id = 100011
  AND order_no = 'USO202606300001'
LIMIT 10
```

结果：

```json
{
  "订单金额": 4752.0,
  "未发件数": 3,
  "是否超时": 1
}
```

业务答案正确，但属于手写物理 SQL 兜底，不是标准语义编译路径。

### 5.4 Q7：占比

## 6. 失败场景分析

### 6.1 Q3、Q8：完整中文日期范围仍无法归一化

两个问题的时间结果均为：

```json
{
  "raw": "2026年6月1日至2026年6月30日",
  "normalized": {
    "raw": "2026年6月1日至2026年6月30日",
    "kind": "unsupported",
    "timezone": "Asia/Shanghai"
  },
  "value_status": "provided"
}
```

校验结果：

```json
{
  "status": "clarification_required",
  "reason_codes": ["time_range_unsupported"],
  "clarification_slots": ["time_range"]
}
```

Q3 的模型思考文本表示要检索语义资产，但没有产生 Tool Call，随后被结果守卫拦截。

Q8 的模型输出了一段包含 `action: clarify` 和两个选项的 JSON 文本，但没有真正调用 `clarify`，也没有创建 `chatbi_agent_clarification` 记录，随后同样被结果守卫拦截。

因此这里包含两个问题：

1. 时间范围归一化仍不支持该明确、完整的中文日期范围。
2. 当上游要求澄清时，模型输出的普通文本没有被转成真实结构化澄清。

数据库基准证明两个问题都有可查询数据。Q8 按相邻日 GMV 绝对变化排序的前三天为：

| 日期 | 当日GMV | 前一日GMV | 变化值 |

| 2026-06-10 | 33362.72 | 6097.68 | +27265.04 |
| 2026-06-11 | 7132.40 | 33362.72 | -26230.32 |
| 2026-06-28 | 31130.24 | 8404.20 | +22726.04 |

### 6.3 Q5：多值筛选正确，但比较查询缺少分组维度

问题理解已正确生成数组：

```json
{
  "name": "档口ID",
  "role": "filter",
  "value": ["100011", "100012"],
  "value_status": "provided"
}
```

语义编译也正确生成 `IN`：

```sql
where fct_stall_order_daily.stall_id in ('100011', '100012')
```

但是编译计划为：

```json
{
  "metric_asset_ids": [271],
  "dimension_asset_ids": []
}
```

缺少店铺维度 `278`，因此 SQL 没有 `GROUP BY stall_id`，只返回：

```json
{"gmv_total": 27404.76}
```

数据库正确基准为：

| 店铺ID | 总GMV |
|---|---:|
| `100012` | 19040.40 |
| `100011` | 8364.36 |

正确结论应为店铺 `100012` 更高。

Agent 在编译后已经意识到缺少分组，但工作状态已经进入 `sql_ready`，再次编译被拒绝；执行后进入 `executed`，再次编译和执行继续被拒绝。最终回答如实说明无法比较，没有编造答案，但业务问题没有完成。

### 8.2 工作状态和工具守卫已经发挥的作用

当前工作状态能够做到：

1. 检索已完成后，将推荐动作收敛到 `compile_semantic_sql`。
2. 编译完成后，将推荐动作收敛到 `execute_sql`。
3. 执行完成后，将推荐动作收敛到 `finish`。
4. 拒绝重复检索、重复编译、重复执行以及不符合当前阶段的 schema 查询。
5. 在 Q5 高消耗场景中保留执行和收口预算，没有在 SQL 执行前终止。

这些守卫保证了错误动作不会修改可信状态，也避免了重复执行真实查询。

### 8.3 尚未解决的问题

守卫发生在模型已经完成一次规划之后。因此模型即使选择了当前不可用工具：

- 仍然消耗一个 Agent 步骤。
- 仍然消耗本轮模型 Token。
- 仍然在消息历史中增加错误 Observation。

本轮共有：

- 4 次重复语义检索被拒绝。
- 2 次编译完成后的再次编译被拒绝。
- 2 次执行完成后的再次执行被拒绝。
- 1 次编译完成后的物理 schema 查询被拒绝。

Q5 最明显：

```text
检索成功
→ 重复检索被拒绝
→ 错误编译
→ 相同错误编译
→ 编译成功
→ 再次编译被拒绝
→ 执行成功
→ 再次编译被拒绝
→ 再次执行被拒绝
→ finish
```

因此，本轮证明“状态守卫和预算保留”有效，但“模型第一次就选择正确工具并构造正确参数”仍未稳定。

## 9. 综合判断

### 9.1 已解决或明显改善

1. 维度值不再进入语义检索。
2. 多值维度可以完整保留为数组，并编译为 SQL `IN`。
3. 商品指标名中的“近7天、近30天”不再污染全局时间范围。
4. 编译成功后通常可以进入 SQL 执行。
5. 本轮没有执行前预算耗尽。
6. 客户数 5 个澄清指标全部可执行。

### 9.2 当前优先级最高的问题

1. **问题理解层的业务结构不变量缺失。**
   - 排名对象应确定为分组和展示维度。
   - 多对象比较应确定为筛选值集合，同时也是比较分组维度。
   - 已配置指标名中的时间修饰不应被拆为全局时间冲突。

2. **时间范围归一化覆盖不足。**
   - 明确的中文起止日期仍输出 `unsupported`。

3. **澄清必须走结构化入口。**
   - 不能把 `action: clarify` JSON 或选项列表作为普通思考文本输出后直接失败。

4. **模型参数错误仍会消耗大量预算。**
   - `order_by: null`、错误 `time_bucket`、遗漏 `dimension_asset_ids` 都应尽量在确定性准备阶段修正或拒绝进入下一状态。

5. **编译后发现计划缺失时缺少安全纠错路径。**
   - Q5 在编译后发现缺少店铺分组，但状态已经锁定为只允许执行。
   - 当前可以防止重复和越序，但不能在“编译产物不满足原始查询形态”时回退并修正计划。

## 10. 最终结论

本轮改造已经解决“维度值检索”“多值 ID 被拼接”“编译后执行预算不足”三个关键问题，Agent 的标准语义路径成功率明显提高；10 个业务场景中有 6 个得到正确答案，Q10 五个澄清分支全部通过。

但系统仍未达到稳定可用。当前失败已经从“语义决策无法执行”转移为更上游和更结构化的问题：时间范围归一化、排名与比较的分组语义、指标名修饰边界，以及澄清和编译计划的确定性约束。工作状态能够阻止错误动作生效，却还不能阻止模型为错误动作消耗步骤和 Token，也不能在编译产物与原始分析形态不一致时安全回退。
