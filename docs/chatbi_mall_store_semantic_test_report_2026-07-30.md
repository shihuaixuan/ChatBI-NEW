# ChatBI“商城店铺主题”具体 ID 问数测试报告

## 1. 测试结论

本轮使用“商城店铺主题”的真实语义资产和业务数据，设计并执行了 10 个不同层面的 Chat Agent 问题。所有对象筛选均使用真实具体 ID；“客户数”问题产生的 5 个指标澄清选项也已逐一选择并实际运行。

当前版本不满足“通过语义层稳定回答具体 ID 问题”的要求：

- 10 个主问题的首次运行中，7 个在问题理解阶段失败。
- 10 个主问题中，标准语义编译成功数为 `0/10`。
- 经过受控重试后，最终得到答案的问题为 `3/10`，但均在语义编译失败后改走物理表手写 SQL。
- 已得到的 3 个答案均与数据库基准值一致，但不能计为语义层通过。
- “客户数”产生的 5 个澄清选项已全部覆盖，标准语义路径通过数仍为 `0/5`。

因此，本轮测试的语义层通过率为 **0%**。主要阻断点不是单个测试案例，而是具体维度值识别、检索决策收敛和澄清状态保持三个公共环节。

## 3. 判定标准

本报告将“答案正确”和“语义层通过”分开判定。

| 判定项 | 通过条件 |
|---|---|
| 问题理解通过 | 模型输出满足 DTO 契约，指标、维度、具体值和时间进入后续流程 |
| 语义检索通过 | 必需槽位完成绑定，决策状态可执行，不是 `partial`、`missed` 或 `ambiguous` |
| 语义编译通过 | `compile_semantic_sql` 成功返回由语义模型生成的 SQL |
| 数据执行通过 | SQL 成功执行并返回结果 |
| 答案正确 | 最终结果与数据库基准值一致 |
| 全链路通过 | 上述环节全部通过，且未绕过语义层手写物理表 SQL |

### 6.1 澄清后的共同异常

用户选择指标后，已选择的资产本应成为后续执行的已确认事实。但实际流程再次调用 `search_semantic_assets` 后，状态重新变为 `semantic_ambiguous`：

1. 已选择的客户数指标再次成为歧义候选。
2. 已经明确的档口 ID 也可能再次进入歧义状态。
3. Agent 重复澄清、重复检索和重复编译。
4. 工具预算被消耗，最终以 `budget_exhausted` 结束。

这说明问题不在某个客户数指标，而在澄清结果与后续检索结果的合并规则。

## 9. 问题定位

### P0-1：具体维度 ID 的问题理解输出不稳定

`DimensionRecognitionOutput.filter_mentions` 的代码契约是 `list[dict[str, Any]]`，但模型经常返回字符串列表。错误发生在公共问题理解输出校验处，所以任何带具体档口、客户或商品值的问题都可能受影响，不是某个 ID 的特殊情况。

实现依据：

- `backend/apps/chatbi/models/dto/question_understanding.py:126`
- `backend/apps/chatbi/orchestration/graph/capabilities/adapters/question_dimension.py:42`

### P0-2：槽位已绑定，但语义决策仍保持不可执行

Q1 正式表达、Q6、Q7 已获得正确的指标、维度值和时间信息，检索决策仍包含 `NO_CANDIDATE_ABOVE_HARD_FILTERS`，整体状态为 `partial/missed`。编译工具随后按规则返回 `semantic_decision_not_executable`。

这说明必需槽位的可执行性判定没有只依据最终有效绑定，仍受未命中子查询或残留检索项影响。

实现依据：

- `backend/apps/retrieval/query/policy.py:162`
- `backend/apps/tool/tools/semantic.py:430`

### P0-3：澄清后的 resolved 状态被重复检索覆盖

5 个客户数分支均表明：用户已经选择指标后，后续重复检索可以把已确认状态重新变成 `semantic_ambiguous`。当前状态合并没有稳定保持用户确认结果，导致重复澄清和预算耗尽。

这与 Agent 提示词中“已确认的问题理解是后续执行的唯一意图事实源”的规则不一致。

实现依据：

- `backend/apps/chatbi/orchestration/agent/prompts.py:33`
- `backend/apps/chatbi/orchestration/agent/tools/interaction.py:61`

### P1-1：无效和重复工具调用快速消耗预算

运行中出现以下行为：

- 对同一不可执行决策重复调用 `compile_semantic_sql`。
- 澄清后重复调用 `search_semantic_assets`。
- 使用错误参数调用 `search_semantic_assets` 或 `get_sql_examples`。
- 构造不在原候选中的澄清绑定，返回 `semantic_clarification_option_invalid`。

这些行为不是最初根因，但会放大 P0 问题，使原本可以继续澄清或明确失败的运行变成 `budget_exhausted`。

### P1-2：手写 SQL 掩盖语义层失败

Q1 变体、Q6、Q7 的数值虽然正确，但均在标准语义编译失败后直接访问物理表。这会造成“最终回答成功”和“语义层可用”混在一起，也会绕开统一指标口径。

## 10. 建议修复顺序

1. 先修复问题理解输出契约：确保具体维度值始终进入结构化 `dimension_slots`，并对 `filter_mentions` 使用单一对象结构；不要针对 `100011` 等案例写特例。
2. 再修复语义决策的业务不变量：只要全部必需槽位已有被允许的最终绑定，非必需检索项的 `missed` 不应把整体决策降为不可执行。
3. 修复澄清状态合并：用户确认的绑定优先级必须高于后续自动检索，重复检索不得覆盖已确认槽位。
4. 在 Agent 循环中阻止相同参数重复编译；`semantic_decision_not_executable` 后只能执行错误详情指定的恢复动作。
5. 最后收紧成功判定：标准语义编译失败后，不应把手写物理 SQL 的回答计为语义层成功，并应在测试指标中单独统计。

## 11. 回归验收条件

完成修复后，应使用本报告相同的 10 个问题和 5 个澄清分支重新运行，并满足：

- 10 个问题的问题理解输出均通过 DTO 校验。
- 具体 ID 全部形成结构化维度筛选，不丢值、不把维度名和值混成字符串。
- 5 个客户数选项选择后不再二次询问相同指标。
- 10 个问题均由 `compile_semantic_sql` 生成 SQL，不允许用手写物理表 SQL 替代。
- SQL 结果与第 7 章数据库基准一致。
- 相同工具与相同参数不发生无意义重复调用。
- 工具预算不因状态回退或重复编译耗尽。
