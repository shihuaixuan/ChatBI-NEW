# ChatBI
## 一、背景

传统 BI 依赖报表、仪表板和专业分析人员。业务用户需要先理解数据口径，再通过固定界面筛选或向数据团队提出需求，分析链路长、响应慢，临时问题尤其难以快速得到答案。

大模型让用户可以直接用自然语言提问，ChatBI 因此成为降低数据分析门槛的重要方向。它的价值不只是 Text-to-SQL，而是完成一条端到端问数链路：

```text
自然语言问题
  → 问题理解与澄清
  → 指标、维度和时间口径识别
  → 数据与知识检索
  → SQL 生成、校验和执行
  → 结果解释与可视化
```

这意味着 ChatBI 不是一个单点模型能力，而是一个由大模型、语义层、数据权限、SQL 执行和交互流程共同构成的智能分析系统。

## 二、核心矛盾

用户希望像聊天一样自由提问，但企业数据分析要求结果严谨、权限可控、过程可解释。**自然语言具有模糊性，数据系统要求确定性。**  ChatBI 的研发目标，就是在两者之间建立一条稳定、可治理的转换链路。

## 三、面临的核心挑战

### 1. 业务语义难以准确对齐

同一个词在不同业务中可能代表不同指标，同一个指标也可能存在多种统计口径。时间范围、过滤条件、维度层级和上下文追问都会进一步增加歧义。

如果问题理解错误，即使 SQL 完全正确，最终答案仍然是错的。

### 2. 端到端链路长，错误会逐级放大

一次问数会经过分类、重写、意图识别、知识检索、SQL 生成、执行和回答等多个环节。任何节点的偏差，都可能传递到后续步骤。

系统必须能够识别歧义、主动澄清、限制重试，并在失败后给出可恢复路径，而不是把所有逻辑堆进一条不可控的模型调用链。

### 3. 准确性与安全性必须同时成立

生成的 SQL 不仅要能执行，还要满足只读限制、数据源边界、行列权限和敏感数据保护要求。

“查得到”不等于“允许查”。权限控制必须进入执行链路，不能只依赖提示词约束。

### 4. 过程必须可观测、可解释、可追责

当答案异常时，研发人员需要快速判断问题发生在语义识别、知识召回、SQL 生成、权限处理还是数据执行。

因此，系统需要节点级状态、输入输出摘要、路由原因、错误分类、执行轨迹和必要的脱敏机制。没有可观测性，ChatBI 就难以调试，更难以规模化交付。

### 5. 效果依赖持续运营，而非一次性交付

模型能力不能自动解决企业内部的指标口径、术语、数据质量和典型问法问题。高质量 ChatBI 需要持续沉淀语义资产、术语库、SQL 示例和用户反馈。

系统不仅要“能回答”，还要支持评估、校准和迭代，形成越用越准的闭环。

### 2. 基于Agentic的模型架构

与图架构的确定性编排相对，Agentic 架构把规划权交给 LLM：模型通过工具调用自主决定每一步做什么（检索语义资产、编译/生成 SQL、执行、向用户澄清、结束作答），系统通过受控工具白名单、预算护栏（步数/token/澄清轮次/超时）和内嵌在工具里的安全守护（只读、权限改写、限行数）约束行为边界。其优势是对长尾问法（模糊探索、多步推理、追问链）的自适应能力；代价是确定性下降与成本上升，因此作为与图主线并行的实验模式，通过同一评测集对照评估。
