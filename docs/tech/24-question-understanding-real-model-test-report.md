## 1. 测试结论

本次基线测试直接调用当时环境配置的真实模型 `deepseek-v4-flash-260425`，经过 Agent 使用的 `QuestionUnderstandingService` 完成问题重写、意图与查询组织方式识别、维度识别、时间归一化和最终确定性校验。

| 模型调用失败数 | 0 |
| 每题模型调用数 | 3 |

主要结论如下：

1. 问题重写、普通指标查询、明确分组、趋势、TopN 数量和排序方向整体表现正确。
2. 对“最近 7 天店铺ID的……”这种用途不明确的维度，校验正确要求澄清，没有擅自确定分组或筛选。
3. 两个排名问题中，模型可能把指标“新增客户数-线上”拆成指标“新增客户数”和残余筛选“线上”。现有校验没有发现指标短语被错误拆分。
4. 排名问题中的维度识别不稳定。意图模型已经输出 `needs_group_by=true`，但维度模型仍可能把“店铺ID”识别为 `ambiguous`。最终校验正确发现没有可用的排名分组维度并阻止执行。
5. 校验阶段能检查结构间的关系，但无法单独判断指标文本是否保真。当前最主要的缺口是指标短语完整性校验，以及意图任务和维度任务之间的业务语义一致性修复。

每个问题依次执行以下阶段：

1. `QUESTION_REWRITE`：重写为可独立理解的问题。
2. `INTENT_RECOGNITION`：识别意图、指标、时间和完整 `query_shape`。
3. `DIMENSION_RECOGNITION`：结合数据集 Schema 识别维度、角色和值。
4. 服务端合并结果，归一化相对时间并派生 `required_slot_types`。
5. 确定性校验检查意图、维度、查询组织方式和时间之间的一致性。
6. 脚本将最终结果逐字段与人工预期对照。

字段准确率计算公式为：`匹配字段数 / 已定义预期的字段数`。这是本次测试集上的字段匹配率，不代表线上所有问题的总体准确率。

## 4. 各用例逐阶段结果

### 4.1 单值筛选指标查询

问题：`今天店铺ID 100011的活跃客户数-线上访问是多少？`

问题重写输出：

| 字段 | 输出 |
| --- | --- |
| `message_type` | `new_question` |
| `rewritten_question` | 原问题保持不变 |
| `need_user_input` | `false` |
| `confidence` | `1.0` |

意图识别输出：

| 字段 | 输出 |
| --- | --- |
| 意图 | `metric_query` |
| 指标 | `活跃客户数-线上访问` |
| 时间 | `今天` |
| 查询方式 | 聚合、不分组、不排序、无限制、无时间粒度 |

维度识别输出：

| 字段 | 输出 |
| --- | --- |
| 标准维度 | `店铺ID` |
| 角色 | `filter` |
| 值 | `100011` |
| 值状态 | `provided` |

服务端合并后将“今天”转换为 `[2026-08-12, 2026-08-13)`，派生必需槽位 `metric、filter、time_dimension`。最终校验为 `valid`，15 个检查全部通过。

### 4.2 明确按店铺分组的指标查询

问题：`最近7天各店铺ID的新增客户数-线上是多少？`

| 阶段 | 关键输出 |
| --- | --- |
| 问题重写 | 保持原问题，`new_question` |
| 意图识别 | `metric_query`；指标 `新增客户数-线上`；`needs_group_by=true` |
| 维度识别 | `店铺ID`，角色 `group_by` |
| 时间归一化 | `[2026-08-06, 2026-08-13)` |

| 最终校验 | `valid` |

该用例 14/14 个字段符合预期，说明“各店铺ID”在两个独立模型任务中的结果一致。

### 4.3 最高 5 个店铺排名

问题：`本月新增客户数-线上最高的5个店铺ID是哪些？`

意图识别正确输出：

- `intent_type=ranking_analysis`
- `needs_group_by=true`
- `needs_order_by=true`
- `order_direction=desc`
- `limit=5`
- 时间为“本月”，归一化为 `[2026-08-01, 2026-09-01)`

维度识别输出存在两个问题：

- 将 `店铺ID` 标记为 `ambiguous`，没有标记为排名所需的 `group_by`。
- 将指标中的“线上”拆成残余筛选 `{name: 线上, value: 线上}`。

最终校验输出：

```json
{
  "status": "clarification_required",
  "reason_codes": [
    "group_by_target_missing",
    "ranking_dimension_missing",
    "dimension_role_ambiguous"
  ],
  "clarification_slots": ["dimension"]
}
```

校验正确发现了排名查询缺少明确分组维度，阻止错误结果进入后续执行。但校验没有发现“新增客户数-线上”被拆成“新增客户数”与“线上筛选”。该用例 11/15 个字段符合预期。

### 4.4 最低 3 个店铺排名

问题：`本月新增客户数-线上最低的3个店铺ID是哪些？`

意图识别正确生成升序和数量限制：

```json
{
  "intent_type": "ranking_analysis",
  "needs_group_by": true,
  "needs_order_by": true,
  "order_direction": "asc",
  "limit": 3
}
```

维度模型同样把 `店铺ID` 标记为 `ambiguous`，并错误拆出“线上”筛选。最终校验与最高 5 个问题相同，返回 `group_by_target_missing`、`ranking_dimension_missing` 和 `dimension_role_ambiguous`，阻止执行。该用例 11/15 个字段符合预期。

这个结果说明模型能够正确区分“最高”对应降序、“最低”对应升序，但维度任务没有利用已经识别出的排名语义。

### 4.5 最近 7 天每日趋势

问题：`查看最近7天每天的活跃客户数-线上访问趋势。`

| 字段 | 输出 |
| --- | --- |
| 意图 | `trend_analysis` |
| 指标 | `活跃客户数-线上访问` |
| 时间范围 | `[2026-08-06, 2026-08-13)` |
| `needs_group_by` | `true` |
| `time_grain` | `day` |
| 维度槽位 | 空，时间粒度承担分组目标 |

该用例 13/13 个字段符合预期。服务端没有根据“每天”补时间粒度，`day` 来自真实模型输出；校验只确认时间粒度与分组声明一致。

| 阶段 | 关键输出 |

该用例 15/15 个字段符合预期。这里的 `clarification_required` 是正确结果，说明校验阶段没有将用途不明确的“店铺ID”自动改成分组或筛选。

## 5. 校验阶段的实际作用

### 5.1 本次测试中成功发现的问题

| 问题 | 校验码 | 作用 |
| --- | --- | --- |
| 查询声明需要分组，但没有有效分组目标 | `group_by_target_missing` | 阻止缺少分组对象的查询继续执行 |
| 排名分析没有明确排名维度 | `ranking_dimension_missing` | 防止产生无法确定 `GROUP BY` 对象的排名 SQL |
| 维度用途不明确 | `dimension_role_ambiguous` | 要求用户确认分组、筛选或忽略 |

两个排名用例中，即使意图模型正确输出了排序方向和数量，维度模型的结果仍与查询组织方式冲突。校验没有用规则强行改写维度角色，而是将结果标记为需要澄清，因此发挥了执行前阻断作用。

### 5.2 本次测试中没有发现的问题

| 问题 | 当前表现 | 原因 |
| --- | --- | --- |
| `新增客户数-线上` 被截断为 `新增客户数` | 没有校验码 | 当前校验只判断指标是否存在，不判断指标短语是否完整 |
| 指标修饰词“线上”被拆成残余筛选 | 没有校验码 | 当前校验只检查残余筛选的基本结构和时间误识别，没有校验它是否属于指标短语 |
| 模型的高置信度与错误结果并存 | 仍保留 `confidence=0.95` | 置信度是模型自报值，当前没有基于跨任务冲突重新计算 |

因此，校验阶段当前主要解决“结构正确但字段关系不成立”的问题，不能证明每个业务短语都理解正确。

## 6. 准确性分析

### 6.1 稳定表现较好的部分

- 6/6 问题重写保持原始问题，没有新增或删除语义。
- 6/6 意图类型符合预期。
- 4 个带明确相对时间且被模型正确拆分的问题，绝对时间范围全部正确。
- Top5 和 Bottom3 的数量全部正确。
- “最高”识别为 `desc`，“最低”识别为 `asc`。
- 明确的“各店铺ID”和用途不明确的“店铺ID”能够在普通指标问题中正确区分。

### 6.2 主要错误模式

排名表达中的“指标 + 业务修饰词 + 排名词 + 维度”是本次最不稳定的结构：

1. 指标模型可能丢失 `-线上` 修饰词。
2. 维度模型可能把排名对象当成用途不明的普通维度。
3. 维度模型进一步把被遗漏的指标修饰词识别为残余筛选。

这不是排序规则问题。两个排名问题的 `order_direction` 和 `limit` 都正确，错误发生在指标边界与排名维度角色识别。

## 7. 建议

以下建议是基于当时串行实现和指标完整性要求形成的历史结论。并行调用与指标候选职责已经落地，最新状态以第 9 章为准。

按影响程度建议后续处理：

1. 维度任务输入增加已经识别出的 `intent_type` 和 `query_shape`。当意图为排名且 `needs_group_by=true` 时，维度模型应结合排名语义判断排名对象，而不是只依据是否存在“各”“按”等词。
2. 增加指标短语边界一致性检查。若维度任务的残余筛选文本来自意图任务已识别的完整指标内部，应视为跨任务冲突，不能直接保留。
3. 对数据集中已存在的完整指标名称进行匹配校验。本次数据集明确存在 `新增客户数-线上`，可以用它发现模型输出的 `新增客户数` 可能丢失修饰词。该步骤应作为校验或候选匹配依据，不应静默替换模型语义。
4. 将模型自报置信度与确定性校验结果分开呈现。只要存在跨任务冲突，不能因为 `confidence=0.95` 就认为理解可靠。

## 9. 优化后实现与复测

### 9.1 实现变化

当前问题理解流程已经调整为：

```text
问题重写
   ↓
   ├─ 意图、指标候选、时间、query_shape
   └─ 维度、维度角色、筛选条件
   ↓
合并与确定性校验
```

与基线版本相比：

1. 意图识别和维度识别在问题重写完成后并行调用。
2. 维度模型不再接收意图模型生成的 `metric_mentions` 和 `time_mentions`，避免串行错误传递。
3. 意图模型的输出契约不再包含具体维度和筛选字段。
4. 维度提示词增加排名对象、明确筛选值和维度用途歧义的完整输入输出示例。
5. 意图提示词增加排名、趋势和普通指标查询的完整输入输出示例。
6. 问题重写提示词增加新问题、追问和上下文不足的完整输入输出示例。
7. `metric_mentions` 被定义为后续语义检索的指标候选，不再要求问题理解阶段确定完整指标口径。
8. 不再因为“新增客户数”和“新增客户数-线上”的文本边界不同而阻断流程。

### 9.5 当前校验职责

当前确定性校验继续负责：

- 查询方式与意图类型是否一致。
- 排序声明、排序方向和数量限制是否一致。
- 时间粒度与分组声明是否一致。
- 分组需求是否存在明确分组目标。
- 排名查询是否具备排名维度、排序和数量限制。
- 维度用途和值是否明确。

指标候选是否与数据集中的最终指标名称完全一致，不属于问题理解校验职责，由后续语义检索完成匹配。
