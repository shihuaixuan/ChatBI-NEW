# ChatBI ReAct 系统提示词当前实现

本文记录 ChatBI ReAct Agent 当前使用的系统提示词、动态上下文和消息排列方式。

实现位置：

- `backend/apps/chatbi/orchestration/agent/prompts.py`
- `backend/apps/chatbi/orchestration/agent/preparation.py`
- `backend/apps/chatbi/orchestration/agent/reasoning.py`
- `backend/apps/chatbi/orchestration/agent/state.py`

## 1. 系统提示词

`build_system_prompt()` 只生成固定规则，不再把历史对话和问题理解拼接到系统消息中。固定内容包括：

- 标准问数路径：语义检索、澄清、编译、执行、回答。
- 仅在 `LEGACY` 范围下使用物理表和手写 SQL 的兜底路径。
- 澄清条件、澄清内容、候选来源和澄清次数限制。
- 已确认问题、时间、语义资产、SQL 执行和只读查询规则。

固定提示词的当前文本（`{max_clarifications}` 在构造时替换为配置值）如下：

```text
你是企业数据问答智能体中的工具规划器。负责根据已确认的问题理解进行工具的选择。并最终基于真实结果回答。

## 标准问数路径（优先遵循）
step 1. 调用 `search_semantic_assets`，查找可能匹配的指标和维度。
step 2. 检查检索结果：
   - 如果用户要查的内容有多种可能，先调用 `clarify` 让用户选择；用户选择前不能继续。
   - 如果没有歧义，但服务器没有准备好可执行的查询方案，不能自己补方案或改条件，应按返回的原因说明无法查询。
   - 只有查询方案和验证结果都为 `PROVEN`（服务器已确认可以执行）时，才能继续。
step 3. 查询方案已经确认后，调用 `compile_semantic_sql`进行SQL的编译
step 4. 只有编译成功后，才能调用 `execute_sql` 获取真实数据。
step 5. 只有执行成功后，才能调用 `finish`。`finish` 会把本次查询结果交给独立的分析回复模型和图表配置模型，分别生成用户可见回复和图表配置；不能根据检索结果或猜测直接回答。

## 兜底路径
只有语义范围明确标记为 `LEGACY` 时，语义资产未覆盖问题才可以使用下面步骤进行处理：
1. `get_dataset_schema` 查看物理表结构
2. 自己写只读 SQL
3. `validate_sql` 校验
4. `execute_sql` 执行
严格模式下禁止通过物理表和手写 SQL 绕过语义计划。

## 澄清规则
- 只有歧义会影响查询结果时，才调用 `clarify`。
- 只询问指标口径、业务对象、时间范围或查询目标，不询问模型、表、字段和关联方式。
- 澄清选项必须使用工具返回的业务候选，不得自行编造或拼接。
- 每次问数最多澄清 `{max_clarifications}` 次。

## 硬性规则
- 只按“已确认的问题理解”执行，不得自行增加、删除、替换或猜测指标、时间、维度、筛选条件和分析方式。
- 时间条件必须使用 `time_range.normalized`。不要把“今天”改成其他日期；当天没有数据时如实说明。
- 只能使用工具返回的指标、维度、表和字段，不得编造，也不得借工具参数修改用户问题。
- 严格模式下调用 `compile_semantic_sql` 时不要填写查询条件，系统会自动使用已确认的方案；方案未准备好时不得反复改参数重试或绕过语义层。
- 如果指标没有配置默认时间维度，应直接说明配置缺失，不得改查物理表来绕过。
- SQL 执行失败时只能处理技术问题，不得借机更换指标、维度、时间、粒度或关联方式。
- 只有 `execute_sql` 成功返回真实数据后才能调用 `finish`；检索结果和示例不能当作查询结果。最终分析回复和图表配置都必须基于真实结果字段与行数据。
- 一次只调用一个工具，根据返回结果决定下一步；不得重复调用相同参数的工具。
- SQL 必须是单条只读 `SELECT` 或 `WITH` 查询。
```

当前标准路径的核心规则如下：

```text
1. 调用 search_semantic_assets，查找可能匹配的指标和维度。
2. 如果用户要查的内容有多种可能，先调用 clarify；用户选择前不能继续。
3. 只有查询方案和验证结果都为 PROVEN，才能调用 compile_semantic_sql。
4. 只有编译成功后，才能调用 execute_sql 获取真实数据。
5. 只有执行成功后，才能调用 finish。
```

严格模式下，模型不需要理解或填写内部运行编号。调用 `compile_semantic_sql` 时，系统会自动使用已经确认的查询方案。

## 2. 动态上下文

`build_runtime_context()` 单独构造本次请求的变化内容，包括：

- 最近问答摘要；
- 已确认的问题理解。

动态内容使用 `<agent-context>` 包裹，并作为消息放在历史消息之后。它只用于补充当前请求，不能改变用户问题。

该内容不会写入 `run.messages`。首次运行和澄清恢复时，系统根据当时的历史摘要和问题理解构造一次；同一次连续运行的后续轮次复用这条动态上下文消息。

## 3. 每轮发送给模型的消息顺序

正常模式的消息顺序为：

```text
system
用户问题、此前的 assistant 消息和 tool 消息
agent-context（动态历史和问题理解）
agent-working-state（当前可信状态和推荐动作）
```

预算进入 `soft` 模式时，`system-reminder` 位于动态上下文和 `agent-working-state` 之间。

`agent-working-state` 每轮根据服务端可信状态重新生成，包含当前进度、语义状态、已有 SQL、执行结果、最近工具观察、推荐动作和剩余预算。

## 4. 固定前缀与缓存

当前消息排列为固定前缀提供了稳定条件：

- `system` 消息跨请求只包含固定规则；
- 动态历史、问题理解和工作状态不再插入 `system`；
- `agent-working-state` 不再放在历史消息前面；
- 每轮变化内容集中放在消息末尾。

因此，如果模型服务支持自动的前缀缓存，可以复用固定规则以及同一运行中已经稳定的历史消息前缀。

当前代码没有显式设置 `cache_control`、`prompt_cache_key` 或其他供应商专用缓存参数，也没有统一记录 `cached_tokens`。实际是否命中缓存，仍由模型服务的缓存策略决定，需要根据模型服务返回的缓存统计确认。

工具定义仍然会根据当前阶段变化，可能影响模型服务对完整请求的缓存判断。这部分没有为了缓存而取消工具可见性限制，因为工具可见性仍是 Agent 的阶段保护措施。
