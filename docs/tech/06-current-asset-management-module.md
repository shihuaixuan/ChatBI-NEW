# 语义资产管理模块说明

**状态：** 当前产品能力说明  
**创建日期：** 2026-05-29  
**适用对象：** 产品经理、业务分析师、数据管理员、后端/前端研发、问数链路维护人员。  
**对应入口：** 前端 `/set/semantic`，页面名称为“语义资产”。  
**对应后端：** `/semantic/*` 接口，核心代码位于 `backend/apps/semantic/`。

## 1. 这个模块是做什么的

语义资产管理模块用于把数据库中的表、字段和 SQL，整理成业务人员能理解、问数系统能使用的“语义资产”。

数据库里通常只有表名、字段名和字段类型，例如：

```text
customers.customer_name
customers.member_level
orders.pay_amount
orders.created_at
```

这些信息对数据库是清楚的，但对自然语言问数并不友好。用户问的是：

```text
女客户的名称、会员等级和注册时间
今天销售额是多少
各会员等级的订单金额
```

系统要稳定回答这些问题，需要先知道：

- 哪些表可以被问。
- 每张表代表什么业务对象。
- 哪些字段是维度。
- 哪些字段是度量。
- 哪些度量可以生成指标。
- 哪些模型之间可以关联。
- 哪些指标和维度应该暴露给某个数据集。
- 用户问题中的业务词应该匹配到哪个指标、维度或维度值。

语义资产管理模块就是用来完成这件事的。

一句话概括：

```text
它把“数据库结构”加工成“可问数、可解释、可生成 SQL 的业务语义层”。
```

## 2. 为什么需要这个模块

如果没有语义资产管理，问数系统通常只能直接读取数据库 Schema，然后把表字段塞给大模型。这种方式存在几个明显问题：

- 表字段是技术语言，用户问题是业务语言，两者不一定能对上。
- 字段名可能很短或很抽象，例如 `amt`、`uv`、`type`。
- 同一个词可能对应多个指标，例如“额度”可能是销售额度、订单额度或总额度。
- 大模型不知道哪些字段可以聚合，哪些字段只能过滤或分组。
- 多表查询时，大模型不知道模型之间应该如何 Join。
- 不同数据集应该暴露不同资产，不能让用户问到所有表。
- 指标口径如果没有统一管理，不同问题可能生成不同 SQL。

语义资产管理的价值是把这些规则提前沉淀下来，减少问数时的猜测。

## 3. 谁会使用这个模块

当前模块面向四类用户。

| 用户 | 主要关注点 |
| --- | --- |
| 业务分析师 | 能否把业务指标、维度、术语配置清楚，让业务人员能自然提问 |
| 数据管理员 | 能否从数据源、表、字段构建可复用的数据集 |
| 产品经理 | 能否理解资产建设流程、功能边界和后续优化点 |
| 研发人员 | 能否知道前端配置最终如何变成运行时 Schema 和 SQL 生成输入 |

对业务使用者来说，最终目标不是“维护一堆表单”，而是让问数体验更稳定：

```text
用户绑定一个数据集后，可以围绕该数据集自然提问；
系统能理解问题中涉及的指标、维度、过滤条件；
系统能基于配置好的语义资产生成 SQL。
```

## 4. 用户能做什么

当前“语义资产”页面支持以下能力：

| 能力 | 用户能完成什么 |
| --- | --- |
| 主题域管理 | 按业务范围组织资产，例如客户域、订单域、档口域 |
| 模型管理 | 把数据源中的表或 SQL 配置成业务模型 |
| 字段分类 | 将字段标记为标识、维度、度量或普通字段 |
| 维度管理 | 管理可筛选、可分组、可展示的业务维度 |
| 指标管理 | 基于度量、字段或已有指标定义业务指标 |
| 数据集管理 | 选择哪些模型、指标、维度暴露给问数 |
| 术语管理 | 维护业务黑话、同义词和跨资产概念 |
| 运行时验证 | 查看数据集最终 Schema，测试问题能匹配到哪些资产 |
| 知识索引重建 | 将数据集内资产写入兼容知识索引和运行时资产文档，为后续检索能力做准备 |

## 5. 推荐使用流程

建议用户按下面顺序建设资产。

```text
1. 创建主题域
2. 创建模型
3. 选择数据源和表
4. 拉取字段
5. 配置字段角色
6. 保存模型并生成维度
7. 从度量生成指标，或手工创建指标
8. 创建数据集
9. 选择数据集暴露的模型、指标、维度
10. 在运行时验证中生成 Schema
11. 输入问题测试 Schema Mapping
12. 在问数页面绑定数据集并提问
```

这条流程的重点是：先建模型，再建指标维度，最后用数据集决定对外暴露范围。

## 6. 核心概念

### 6.1 主题域

主题域用于按业务范围组织资产。

例如：

- 客户相关数据。
- 订单交易数据。
- 档口经营数据。
- 商品访问数据。

一个主题域下面可以有多个模型、多个数据集和多个术语。

主题域的作用不是直接生成 SQL，而是帮助用户管理资产边界。用户在页面顶部选择主题域后，页面会只展示该主题域下的模型、指标、维度、数据集和术语。

### 6.2 模型

模型是语义资产管理的核心。

模型可以理解为“一个可查询的业务对象”。它通常绑定一张物理表，也可以绑定一段 SQL。

例如：

| 模型 | 绑定来源 | 业务含义 |
| --- | --- | --- |
| 客户模型 | `customers` 表 | 描述客户基础信息 |
| 订单模型 | `orders` 表 | 描述订单交易事实 |
| 商品访问模型 | `product_visit_daily` 表 | 描述商品访问行为 |

模型中会维护字段，并把字段分成四类：

| 字段角色 | 说明 | 示例 |
| --- | --- | --- |
| 标识 | 用于唯一标识业务对象或关联其他模型 | `customer_id`、`order_id` |
| 维度 | 用于筛选、分组或展示 | `gender`、`member_level`、`register_date` |
| 度量 | 可以聚合计算的数值字段 | `pay_amount`、`visit_uv` |
| 普通字段 | 暂不作为语义资产暴露 | 备注、扩展字段 |

模型保存后，系统会把模型中的维度字段自动生成维度资产。度量字段不会自动成为指标，需要用户在指标页选择生成。

### 6.3 度量

度量是模型内部的可计算数值项，通常来自字段。

例如：

- `pay_amount`
- `visit_uv`
- `order_count`
- `follow_uv`

度量本身属于模型详情 `model_detail.measures`，还不是最终对用户开放的指标。

这样设计的原因是：不是所有数值字段都应该直接作为业务指标对外暴露。用户可以先在模型里维护度量，再选择哪些度量生成指标。

### 6.4 指标

指标是用户真正会问、系统需要稳定回答的业务口径。

例如：

| 指标 | 可能的定义 |
| --- | --- |
| 销售额 | `sum(pay_amount)` |
| 访问人数 | `sum(visit_uv)` |
| 客单价 | `销售额 / 支付买家数` |
| 转化率 | `转化人数 / 访问人数` |

当前指标支持三种定义方式：

| 定义方式 | 适用场景 |
| --- | --- |
| 按度量 | 从模型中的度量快速创建指标 |
| 按字段 | 直接基于模型字段写表达式 |
| 按已有指标 | 基于已有指标组合生成派生指标 |

在问数链路中，指标会进入数据集运行时 Schema，供问题理解和 SQL 生成使用。

### 6.5 维度

维度用于描述“按什么看”“筛选什么”“展示什么”。

例如：

- 性别。
- 会员等级。
- 注册时间。
- 档口。
- 商品类目。
- 城市。

维度可以用于：

- `select` 展示字段。
- `where` 过滤条件。
- `group by` 分组字段。

例如用户问：

```text
性别为女的用户的名称与会员等级和注册时间
```

其中：

- “性别”是过滤维度。
- “女”是维度值。
- “用户名称”“会员等级”“注册时间”是需要展示的维度。

### 6.6 数据集

数据集是面向问数用户暴露的资产集合。

模型解决“数据怎么查”，数据集解决“用户能问什么”。

一个数据集可以绑定一个或多个模型，并配置每个模型暴露哪些指标和维度。

例如：

```text
客户相关数据集
  -> 客户模型
      -> 暴露：客户名称、性别、会员等级、注册时间
  -> 订单模型
      -> 暴露：订单金额、订单数、支付时间
```

用户在问答前绑定数据集后，系统应该只在该数据集范围内理解问题和生成 SQL。

### 6.7 术语

术语用于维护业务黑话、同义词和跨资产概念。

例如：

| 术语 | 可能关联 |
| --- | --- |
| 人气 | 访问人数、访问次数 |
| 转化 | 转化人数、转化率 |
| 互动 | 分享人数、关注人数、咨询人数 |
| 额度 | 销售额度、订单额度、总额度 |

术语不是用来重复指标和维度名称的。指标和维度自身已经有名称、英文标识、别名和描述。术语更适合处理“业务上常说，但不是单一字段名”的表达。

当前后端已经支持术语关联指标和维度，但前端页面暂时只提供名称、别名和描述的基础维护。

### 6.8 运行时 Schema

运行时 Schema 是系统把数据集内资产整理后的最终结构。

它包含：

- 数据库类型。
- 数据库版本。
- 数据集信息。
- 模型列表。
- 模型关系。
- 指标列表。
- 维度列表。
- 维度值列表。
- 术语列表。
- 查询配置。

运行时 Schema 是问数链路的输入。用户在页面上的配置，最终都会被转换成这个结构。

当前实现中，运行时 Schema 优先从规范化表读取资产，包括模型字段、模型度量、维度值、数据集模型配置和数据集暴露资产；如果旧数据还只有 JSON 快照，后端会兼容读取 `model_detail`、`data_set_detail`、`type_params`、`dim_value_maps`。

## 7. 各子模块说明

### 7.1 主题域管理

入口：语义资产页面的“主题域”Tab。

用户可以：

- 新建主题域。
- 编辑主题域。
- 删除主题域。
- 在页面顶部切换当前主题域。

主题域会影响页面中其他资产的展示范围。切换主题域后，模型、指标、维度、数据集和术语都会按当前主题域重新加载。

删除主题域时，后端会删除该主题域下的模型、指标、维度、数据集、术语和知识索引。

### 7.2 模型管理

入口：语义资产页面的“模型”Tab。

用户可以：

- 新建模型。
- 编辑模型。
- 删除模型。
- 按模型筛选指标和维度。

新建模型时，用户先选择数据源和表。系统会从数据源中拉取表和字段，并根据字段名、字段类型进行初步分类。

默认推断规则如下：

| 字段情况 | 默认角色 |
| --- | --- |
| 字段名为 `id` 或以 `_id` 结尾 | 标识 |
| 字段类型或字段名像时间 | 维度 |
| 字段类型是数值类型 | 度量 |
| 其他字段 | 维度 |

用户可以在保存前修改这些分类。

模型保存后会写入：

- 模型基础信息。
- 绑定数据源。
- 表或 SQL 来源。
- 模型过滤条件。
- 字段列表。
- 标识列表。
- 维度列表。
- 度量列表。

当前新建模型会自动创建维度，但不会自动创建指标。

### 7.3 指标管理

入口：语义资产页面的“指标”Tab。

用户可以：

- 查看当前主题域下所有指标。
- 按模型筛选指标。
- 从模型度量批量生成指标。
- 手工创建指标。
- 编辑指标。
- 删除指标。

指标创建时需要选择模型。不同定义方式下，用户需要选择不同依赖项。

| 定义方式 | 用户需要选择 | 用户需要填写 |
| --- | --- | --- |
| 按度量 | 模型中的度量 | 指标表达式、默认聚合、过滤条件 |
| 按字段 | 模型字段 | 指标表达式、过滤条件 |
| 按已有指标 | 同模型下已有指标 | 指标表达式、过滤条件 |

“从度量生成指标”是快速初始化能力。它会列出模型里的所有度量，用户勾选后批量生成同名指标。

如果某个度量已经有同 `biz_name` 的指标，系统会跳过，不重复创建。

### 7.4 维度管理

入口：语义资产页面的“维度”Tab。

用户可以：

- 查看当前主题域下所有维度。
- 按模型筛选维度。
- 新建维度。
- 编辑维度。
- 删除维度。

维度一般来自模型字段分类，也可以手工创建。

当前维度页面展示：

- 维度名称。
- 英文标识。
- 所属模型。
- 维度类型。
- 语义类型。
- 维值映射数量。
- 别名。

需要注意：后端支持维度值映射，但当前前端还没有完整的维度值映射编辑能力。

### 7.5 数据集管理

入口：语义资产页面的“数据集”Tab。

用户可以：

- 新建数据集。
- 编辑数据集。
- 删除数据集。
- 选择数据集包含哪些模型。
- 配置每个模型暴露全部资产还是部分资产。

数据集是问数最重要的边界。

配置数据集时，每个模型有两种方式：

| 方式 | 用户操作 | 效果 |
| --- | --- | --- |
| 全部暴露 | 打开“全部暴露” | 该模型下所有已启用指标和维度进入数据集 |
| 手动选择 | 关闭“全部暴露” | 用户手动选择指标和维度 |

问数时，系统应该只使用当前绑定数据集中的资产理解问题。

### 7.6 术语管理

入口：语义资产页面的“术语”Tab。

用户可以：

- 新建术语。
- 编辑术语。
- 删除术语。
- 维护术语别名和描述。

术语用于提升自然语言理解能力，尤其是处理业务黑话和同义表达。

例如用户问：

```text
今天人气怎么样
```

如果“人气”被维护为术语，并关联了“访问人数”“访问次数”等指标，系统就可以把这个词扩展到候选指标。

当前后端数据结构支持术语关联指标和维度，但前端页面还没有完整暴露关联配置。

### 7.7 运行时验证

入口：语义资产页面的“运行时验证”Tab。

该模块不是给普通业务用户日常使用的，更偏向资产管理员和研发调试。

它包含三个能力：

| 能力 | 用户操作 | 作用 |
| --- | --- | --- |
| Schema 预览 | 选择数据集，点击生成 Schema | 查看数据集最终暴露了哪些模型、指标、维度、术语 |
| Schema Mapping | 输入问题，点击映射 | 查看问题命中了哪些语义资产 |
| 重建知识索引 | 选择数据集，点击重建 | 将数据集资产写入兼容知识索引和运行时资产文档 |

Schema 预览可以帮助用户检查数据集配置是否正确。

Schema Mapping 可以帮助用户检查：

- 问题中的指标是否能被识别。
- 问题中的维度是否能被识别。
- 问题中的维度值是否能被识别。
- 别名是否配置有效。

重建知识索引后，后端会同时写入两类运行时数据：

- `headless_schema_index`：保留旧兼容索引结构，供已有调试和兼容链路继续读取。
- `headless_asset_document`：保存数据集视角下的资产文档，包含业务文本、技术文本、别名文本、检索文本和资产快照。

后端已经提供 `GET /semantic/datasets/{dataset_id}/asset-documents` 调试接口，可按资产类型和资产 ID 查看运行时资产文档。前端调试入口还没有完整接入。

## 8. 子模块之间如何关联

语义资产不是孤立维护的，各子模块之间有明确关系。

```text
主题域
  -> 模型
      -> 字段
      -> 标识
      -> 维度
      -> 度量
  -> 指标
  -> 数据集
  -> 术语

数据集
  -> 选择模型
  -> 选择指标
  -> 选择维度
  -> 生成 DataSetSchema

DataSetSchema
  -> Schema Mapping
  -> Ontology
  -> Semantic SQL Compiler
```

更具体地说：

| 上游模块 | 下游影响 |
| --- | --- |
| 数据源 | 决定模型可以选择哪些表和字段 |
| 主题域 | 决定模型、数据集、术语的管理范围 |
| 模型 | 决定指标、维度、SQL 生成的数据来源 |
| 模型字段 | 决定哪些字段可成为维度或度量 |
| 度量 | 可以批量生成指标 |
| 指标 | 进入数据集后，可被用户问题召回并生成聚合 SQL |
| 维度 | 进入数据集后，可用于展示、过滤和分组 |
| 术语 | 进入数据集运行时 Schema 后，可增强问题理解 |
| 数据集 | 决定问数时可见资产范围 |
| 模型关系 | 决定多模型查询时如何 Join |

### 8.1 当前后端表关系

当前 Semantic 资产存储已经从“主表 + 大 JSON”升级为“主资产表 + 规范化子表 + JSON 快照兼容”。核心表关系如下。

```text
headless_domain
  -> headless_model
      -> headless_model_field
      -> headless_model_measure
      -> headless_metric
      -> headless_dimension
          -> headless_dimension_value
  -> headless_model_relation
      -> left_model_id/right_model_id 指向 headless_model
  -> headless_dataset
      -> headless_dataset_model_config
          -> model_id 指向 headless_model
      -> headless_dataset_asset
          -> asset_type + asset_id 指向 headless_metric/headless_dimension
      -> headless_asset_document
      -> headless_schema_index
  -> headless_term

headless_asset_alias
  -> asset_type + asset_id 指向 FIELD/MEASURE/METRIC/DIMENSION/VALUE/TERM 等资产

headless_asset_relation
  -> source_type + source_id 指向来源资产
  -> target_type + target_id 指向目标资产
```

表之间的主要业务关系如下。

| 表 | 上游/归属 | 下游/关联 | 作用 |
| --- | --- | --- | --- |
| `headless_domain` | 工作空间 `oid` | 模型、数据集、术语、模型关系 | 主题域边界，组织一组业务资产 |
| `headless_model` | `headless_domain`、数据源 | 字段、度量、指标、维度 | 描述一个可查询业务对象，绑定表或 SQL |
| `headless_model_field` | `headless_model` | 维度、度量、指标依赖字段、统一别名 | 规范化保存模型字段，替代只依赖 `model_detail.fields` |
| `headless_model_measure` | `headless_model`、可关联字段 | 指标、统一别名 | 规范化保存模型度量，支撑“基于度量创建指标” |
| `headless_metric` | `headless_model`、度量/字段/已有指标 | 数据集暴露资产、资产关系、资产文档 | 对外可问的业务指标，保存表达式、依赖字段、质量状态 |
| `headless_dimension` | `headless_model`、字段 | 维度值、数据集暴露资产、资产关系、资产文档 | 对外可展示、过滤、分组的业务维度 |
| `headless_dimension_value` | `headless_dimension` | 统一别名、资产关系、资产文档 | 独立保存维度值和维值别名 |
| `headless_model_relation` | `headless_domain` | 左右模型 | 保存模型之间的 Join 类型和 Join 条件 |
| `headless_dataset` | `headless_domain` | 数据集模型配置、暴露资产、资产文档、兼容索引 | 问数边界，决定用户绑定数据集后能问什么 |
| `headless_dataset_model_config` | `headless_dataset` | `headless_model` | 规范化保存数据集绑定了哪些模型、是否全部暴露 |
| `headless_dataset_asset` | `headless_dataset`、`headless_model` | 指标/维度 | 规范化保存数据集暴露哪些指标和维度 |
| `headless_term` | `headless_domain` | 资产关系、资产文档 | 保存业务术语、别名和关联资产 |
| `headless_asset_alias` | 各类资产 | 问题理解、资产文档 | 统一保存字段、度量、指标、维度、维值、术语的别名 |
| `headless_asset_relation` | 各类资产 | 各类资产 | 统一保存 `USES_FIELD`、`DEFINED_BY_MEASURE`、`ANALYZABLE_BY`、`BELONGS_TO`、`RELATED_TO`、`EXPOSED_BY_DATASET` 等关系 |
| `headless_asset_document` | `headless_dataset`、运行时 Schema | 后续检索/调试 | 保存数据集视角下的资产检索文档和资产快照 |
| `headless_schema_index` | `headless_dataset`、运行时 Schema | 兼容调试/旧索引读取 | 保留旧结构的 Schema 索引兼容表 |

### 8.2 当前写入和读取规则

资产写入采用“双写兼容”策略：

- 前端仍可以按原 JSON 结构提交模型和数据集配置。
- 后端保存时同步写入规范化表，例如 `headless_model_field`、`headless_model_measure`、`headless_dataset_model_config`、`headless_dataset_asset`。
- 同时保留 `model_detail`、`data_set_detail`、`type_params`、`dim_value_maps`，保证当前前端返回结构兼容。
- 构建 `DataSetSchema` 时优先读取规范化表；规范化表为空时回退读取旧 JSON 快照。

当前版本还增加了资产治理字段：

- `headless_model.schema_version` 和 `last_schema_sync_at`：模型字段/度量同步后递增版本并记录同步时间。
- `headless_dataset.schema_version`：模型结构或数据集暴露范围变化后递增，用于标识运行时 Schema 需要刷新。
- `headless_dataset.index_version`：知识重建后递增，用于标识资产文档版本。
- `headless_metric.quality_status` 和 `quality_message`：保存指标质量校验结果。无效指标不会阻断保存，但默认不会进入 `DataSetSchema`。

### 8.3 资产关系表如何表达业务关系

`headless_asset_relation` 是统一资产关系表，不只表达模型 Join，还表达语义资产之间的依赖和可分析关系。

| 关系类型 | 来源资产 | 目标资产 | 含义 |
| --- | --- | --- | --- |
| `USES_FIELD` | 指标/维度 | 字段 | 指标或维度依赖哪个模型字段 |
| `DEFINED_BY_MEASURE` | 指标 | 度量 | 指标由哪个模型度量生成 |
| `DEFINED_BY_METRIC` | 指标 | 指标 | 派生指标依赖哪些已有指标 |
| `ANALYZABLE_BY` | 指标 | 维度 | 指标可以按哪些维度分析 |
| `BELONGS_TO` | 维度值 | 维度 | 维度值属于哪个维度 |
| `RELATED_TO` | 术语 | 指标/维度 | 术语关联哪些业务资产 |
| `EXPOSED_BY_DATASET` | 数据集 | 指标/维度 | 数据集对外暴露哪些资产 |

这张表的作用是把原来分散在多个 JSON 字段里的关系统一沉淀下来，为后续资产检索、问题理解、影响分析和 SQL 生成提供结构化依据。

## 9. 用户操作示例

假设用户要建设“客户相关数据集”，并支持问题：

```text
性别为女的用户的名称与会员等级和注册时间
```

推荐配置步骤如下。

### 9.1 创建主题域

创建主题域：

```text
名称：客户域
英文标识：customer_domain
```

### 9.2 创建客户模型

选择数据源，选择 `customers` 表，拉取字段。

字段分类示例：

| 字段 | 角色 | 名称 | 英文标识 |
| --- | --- | --- | --- |
| `customer_id` | 标识 | 客户ID | `customer_id` |
| `customer_name` | 维度 | 客户名称 | `customer_name` |
| `gender` | 维度 | 性别 | `gender` |
| `member_level` | 维度 | 会员等级 | `member_level` |
| `register_date` | 维度 | 注册时间 | `register_date` |

保存模型后，系统会生成这些维度。

### 9.3 创建数据集

创建数据集：

```text
名称：客户相关数据集
英文标识：customer_dataset
```

选择客户模型，并暴露客户名称、性别、会员等级、注册时间等维度。

### 9.4 运行时验证

进入“运行时验证”，选择“客户相关数据集”，点击生成 Schema。

检查 `dimensions` 中是否包含：

- `customer_name`
- `gender`
- `member_level`
- `register_date`

然后在 Schema Mapping 中输入：

```text
性别为女的用户的名称与会员等级和注册时间
```

检查系统是否能命中：

- 性别。
- 客户名称。
- 会员等级。
- 注册时间。

如果“女”没有被识别为维度值，需要补充维度值映射能力或在后续理解节点中处理该过滤条件。

## 10. 运行时如何使用这些资产

用户在页面上配置的资产，最终会进入问数运行时。

运行时使用链路如下：

```text
用户问题
  -> 已绑定数据集
  -> 加载 DataSetSchema
  -> 识别问题中的指标、维度、维度值、术语
  -> 生成结构化 slots
  -> Semantic SQL Compiler 读取 DataSetSchema 和 slots
  -> 生成 SQL
```

当前 `Semantic SQL Compiler` 会依赖这些资产：

| 资产 | 运行时用途 |
| --- | --- |
| 数据集 | 确定可问范围 |
| 模型 | 确定 SQL 的表或子查询 |
| 模型过滤 | 自动拼接模型级 where 条件 |
| 指标 | 生成聚合表达式 |
| 维度 | 生成 select、where、group by |
| 模型关系 | 生成 join |
| 数据库类型 | 后续用于适配 SQL 方言 |
| 资产关系 | 后续用于问题理解、候选扩展和影响分析 |
| 资产文档 | 后续用于资产检索、调试和 embedding 召回 |

如果资产配置不完整，SQL 生成会受到影响。

例如：

- 没有数据集：不知道用户能问什么。
- 数据集没有绑定模型：没有查询来源。
- 指标没有表达式：无法生成聚合 SQL。
- 维度没有表达式：无法生成展示或过滤字段。
- 多模型没有 Join 关系：无法生成跨模型 SQL。

## 11. 当前能力边界

当前模块已经能支撑基础语义资产建设，但还不是完整成熟的 Semantic 资产平台。

### 11.1 已经具备的能力

当前已经具备：

- 主题域管理。
- 模型管理。
- 数据源表发现。
- 表字段发现。
- 字段角色推断。
- 字段角色手工调整。
- 模型维度自动生成。
- 模型度量维护。
- 模型字段和模型度量规范化存储。
- 从度量批量生成指标。
- 指标手工创建和编辑。
- 指标表达式、依赖字段和派生指标引用的基础质量校验。
- 维度手工创建和编辑。
- 维度值规范化存储和运行时 Schema 构建。
- 数据集模型绑定。
- 数据集资产暴露范围配置。
- 数据集模型配置和暴露资产规范化存储。
- 术语基础维护。
- 统一资产别名存储。
- 统一资产关系存储。
- 数据集运行时 Schema 预览。
- Schema Mapping 调试。
- 知识索引重建。
- 运行时资产文档生成。
- 资产文档调试接口。
- 模型和数据集 Schema 版本维护。
- 数据集索引版本维护。
- 支撑 Semantic SQL Compiler 读取资产生成 SQL。

### 11.2 当前还不完整的地方

当前主要缺口如下：

| 缺口 | 影响 |
| --- | --- |
| 模型关系前端管理还不够完整 | 后端已有 `headless_model_relation`，但用户配置 Join 的体验还需要继续完善 |
| 维度值映射没有完整前端管理 | 后端已有 `headless_dimension_value`，但“女”“华东”“一号档口”等维值还缺少完整页面维护入口 |
| 术语关联指标/维度没有完整前端入口 | 后端已有 `RELATED_TO` 关系能力，但页面仍偏基础维护 |
| Schema Mapping 仍是子串匹配 | 对口语化问题、同义词、错别字支持不足 |
| 资产文档未成为主召回路径 | 重建后已有 `headless_asset_document`，但还没有真正驱动 Schema Mapping 或问数理解 |
| Semantic embedding 召回尚未实现 | 资产文档已有文本基础，但还没有向量化索引和混合召回 |
| SQL 模型字段解析能力不足 | SQL 来源模型主要依赖人工添加字段 |
| 旧 Semantic 与 Semantic 并存 | 容易出现不同链路读取不同资产体系 |

## 12. 与旧语义资产模块的关系

项目中仍然存在旧的 `/semantic/*` 模块。

旧模块主要包括：

- `SemanticMetric`
- `SemanticDimension`
- `SemanticDimensionValue`
- 指标/维度审核。
- embedding 重建。
- 候选初始化。
- 表达式校验。
- 运行时资产文档。
- 资产质量检查。
- `/semantic/assets/debug/*` 调试接口。

当前“语义资产”前端主页面已经接入 `/semantic/*`，所以实际用户操作主链路是 Semantic。

两套体系的当前关系可以理解为：

| 体系 | 当前定位 |
| --- | --- |
| Semantic 资产体系 | 当前产品主入口，负责 Domain、Model、Metric、Dimension、DataSet |
| 旧 Semantic 资产体系 | 历史能力，部分旧问数链路和调试能力仍可能依赖 |

后续如果要产品化，需要决定：

- 是把旧 semantic 能力迁移到 Semantic。
- 还是保留旧 semantic 作为兼容层。
- 或者明确两套资产分别服务不同问数链路。

## 13. 产品视角总结

当前语义资产管理模块的产品定位是：

```text
让用户把数据库表字段配置成业务可理解的数据集，
并让问数系统基于这些配置进行问题理解和 SQL 生成。
```

它的核心不是“管理指标维度列表”，而是建立一条完整的资产建设链路：

```text
主题域
  -> 模型
  -> 字段分类
  -> 维度和度量
  -> 指标
  -> 数据集
  -> 运行时 Schema
  -> 问数理解和 SQL 生成
```

当前版本已经具备基础可用能力，适合单模型或简单多模型的数据集建设。若要进一步接近成熟的 Semantic BI，需要继续完善模型关系、维度值、术语关联的前端配置体验，并把资产文档、统一别名和统一资产关系真正接入 Schema Mapping、embedding 混合召回和问数理解链路。
