# 问题理解阶段

> **P0 实现勘误（2026-08-16）**：当前问题理解为“上下文化重写 + 单次统一理解”两次模型调用，不再分别调用意图、指标、维度识别模型。统一理解同时输出 `category`、意图、指标、维度、筛选值、排名与查询形态；服务端随后执行一致性校验。所有非 valid 的 `reason_code` 统一进入 `clarification_catalog.py`，得到可恢复澄清卡片或带建议问法的拒答，不再允许进入零工具状态。筛选值的 canonical value 归一发生在后续 Retrieval VALUE 槽，不由理解模型直接决定。

问题理解阶段不是简单调用一次大模型，让模型自由判断用户想查什么。当前实现是一个“模型分工识别、严格结构约束、服务端一致性校验”的前置处理阶段；实际时间解析由 ReAct 中的时间 Tool 完成。

它发生在 Agent 进入 ReAct 循环之前，目标是把用户的自然语言问题转换成一份结构化、经过校验的问题理解结果，作为后续语义检索、时间解析、查询计划、SQL 生成和回答阶段共同使用的依据。

## 贯穿全文的示例

以下使用同一个问题说明各模块如何协作。

| 项目 | 示例内容 |
| --- | --- |
| 最近一次成功问题 | `查询本月销售额` |
| 用户当前问题 | `那最近 7 天门店的呢？` |
| 当前数据集维度 | 假设存在标准维度“门店”，别名包含“店铺” |
| Run 固定时间 | 假设为 `2026-08-12 10:00:00+08:00`，时区为 `Asia/Shanghai` |
| 用户后续澄清 | `按门店分组查看` |

这个问题同时包含以下特点：

- “那……呢”表明它依赖上一轮，是追问。
- 当前问题省略了指标，需要从最近一次成功问题继承“销售额”。
- “最近 7 天”是需要转换为绝对日期范围的相对时间。
- “门店”没有明确表示按门店分组，还是筛选某个门店，需要先澄清。

以下结构化字段是依据当前提示契约和服务端规则给出的预期结果，用于说明字段如何流转。实际运行中的置信度数值以及 `inherited_context` 的具体字段由模型返回。

## 一、问题理解阶段做了什么

### 1. 获取会话上下文

系统首先读取两类上下文：

- 最近若干轮问答摘要，后续会放入 Agent 的动态上下文消息中。
- 同一会话、同一数据源下，最近一次成功执行的问题重写结果。

问题重写只使用最近一次成功执行的问题，不直接使用失败问题，避免错误理解影响后续追问。

在贯穿示例中，上一轮成功问题是：

> 查询本月销售额

用户继续提问：

> 那最近 7 天门店的呢？

系统会结合上一轮成功问题，把当前问题重写为：

> 查询最近 7 天门店的销售额

这里继承的是“销售额”，而“最近 7 天”和“门店”来自当前问题。本轮明确表达的内容优先，不能继续沿用上一轮的“本月”。

注意：1. 若用户是针对上上个问题的追问，那么只根据上一轮的成功回答就不对啦
     2. 最近若干轮问答摘要，这个摘要是什么时候对进行的摘要总结，是每次回答完都要吗，那摘要会不会和上一轮回复的内容做重复？
### 2. 对用户问题进行上下文化重写

第一个模型任务只负责问题重写，判断当前输入属于：

- 新问题 `new_question`
- 基于上文的追问 `followup`
- 对澄清问题的回复 `clarification_reply`

这个任务只负责补全语言上下文，不识别语义资产 ID、字段名、表名和指标口径，也不生成 SQL。

它输出的核心内容包括：

- 重写后的完整问题
- 消息类型
- 从上文继承的内容
- 是否仍然需要用户补充信息
- 缺少的上下文槽位
- 置信度

在贯穿示例中，这一步可以形成如下结果：

| 字段 | 示例结果 |
| --- | --- |
| `message_type` | `followup` |
| `rewritten_question` | `查询最近 7 天门店的销售额` |
| `inherited_context` | 继承上一轮的指标“销售额” |
| `need_user_input` | `false`，因为问题已经能被重写为完整问题 |
| `missing_slots` | 空数组 |

这里的 `need_user_input=false` 只表示问题重写不缺上下文，不代表整个问题理解已经可以执行。后面的维度识别仍可能发现需要用户确认的内容。

### 3. 识别分析意图、指标和时间

问题重写完成后，第二个模型任务与第三个模型任务并行执行。第二个任务识别用户想进行什么类型的分析。目前支持的主要意图包括：

- 指标查询
- 趋势分析
- 排名分析
- 对比分析
- 明细查询
- 占比分析
- 异常分析
- 无法识别

同时识别：

- 可供后续语义检索使用的指标候选
- 用户提到的时间表达
- 查询明细还是聚合结果
- 是否分组、是否排序、排序方向、数量限制和时间粒度
- 意图中存在的歧义或冲突

指标识别在这一阶段不负责最终确定指标口径。例如，模型可以从“新增客户数-线上”中输出“新增客户数”作为检索候选，后续语义检索再结合数据集中的指标名称、别名和定义确定最终指标。查询时间应独立进入时间字段，不应为了扩大指标候选而并入指标文本。

这个任务不负责识别维度和筛选条件，避免一个模型任务同时处理过多内容。

在贯穿示例中，这一步的主要结果是：

| 字段 | 示例结果 |
| --- | --- |
| `intent_type` | `metric_query` |
| `metric_mentions` | `销售额` |
| `time_mentions` | `最近 7 天` |
| `time_range.raw` | `最近 7 天` |
| `query_shape.select_mode` | `aggregate` |
| `query_shape.needs_group_by` | `false`，因为“门店”的用途尚未明确 |
| `query_shape.needs_order_by` | `false` |
| `query_shape.limit` | `null` |
| 维度相关字段 | 暂时保持为空，交给独立维度任务 |

此时模型只确认“查销售额”和“时间为最近 7 天”，还不会决定“门店”是分组维度还是筛选条件。

### 4. 独立识别维度、维度用途和筛选值

第三个模型任务与意图任务并行，专门处理维度。它只接收重写问题、会话继承信息和当前数据集维度候选，不接收意图任务生成的指标、时间或查询组织方式，避免一个模型的错误直接影响另一个模型。它需要识别：

- 用户提到了哪些维度
- 维度用于分组还是筛选
- 用户是否提供了明确筛选值
- 一个维度是否包含多个筛选值
- 哪些条件暂时无法归属到已有维度

例如：

| 用户问题 | 识别结果 |
| --- | --- |
| 查询最近 7 天门店的销售额 | “门店”的用途不明确，需要澄清 |
| 今天各门店的客户数 | “门店”用于分组 |
| 今天 1 号门店的客户数 | “门店”用于筛选，筛选值是“1号” |
| 比较店铺 100011 和 100012 的 GMV | “店铺”用于筛选，筛选值是两个店铺编号 |

因此，贯穿示例会产生一个待确认的维度槽位：

| 字段 | 示例结果 |
| --- | --- |
| `name` | `门店` |
| `role` | `ambiguous` |
| `value` | `null` |
| `value_status` | `not_provided` |

“门店”没有“各”“按”等分组标记，也没有“1号店”这样的具体值，所以系统不能直接决定其用途。

#### 4.1. 使用当前数据集维度内容增加维度识别

维度识别不是只依赖模型的通用理解能力。系统会读取当前语义数据集中的维度信息，包括：

- 标准维度名称
- 维度别名
- 是否属于时间维度
- 已知维度值

然后由服务端统一处理：

- 把别名转换为标准维度名称
- 把问题中出现的已知维度值补充到对应槽位
- 防止时间维度进入普通维度筛选
- 去除重复的筛选条件

如果已经绑定语义数据集，但 Schema 无法加载，系统会明确终止问题理解，不会在缺少必要信息时继续猜测。

在贯穿示例中，假设数据集的标准维度名称是“门店”，别名包含“店铺”。用户使用的是标准名称，因此规范化后仍为“门店”。如果用户问的是“那最近 7 天店铺的呢？”，服务端也会把“店铺”统一为标准名称“门店”。

该步骤只统一自然语言维度名称，不会在这里把“门店”绑定到某张表的 `store_name` 字段；具体资产和字段绑定由后续语义检索与查询计划处理。

### 5. 处理时间表达

系统使用当前 Agent Run 创建时固定的时间上下文解释相对时间。时间上下文包括：

- 基准时间
- 时区
- 自然周起始日
- 财年字段（仅保留在结构化兼容契约中，当前 JioNLP 文本解析不使用）
- 语言区域

因此，“今天”“本月”“最近 7 天”等表达，在同一次 Run 的重试、澄清恢复和回放过程中会保持相同含义，不会因为跨天或服务器时区不同而变化。

当前时间处理支持三种方式：

- 默认 Agent 方式：问题理解只保存 `time_range.raw`，ReAct 首轮调用 `parse_time_range`，由 JioNLP 和项目适配层生成绝对日期范围。
- 模型旁路观察：模型生成时间计划，只用于和默认结果比较，不参与检索、查询计划和 SQL。
- 模型权威方式：模型识别时间语义，服务端校验时间计划并计算绝对日期。

代码中的模型旁路观察和模型权威方式默认关闭。如果部署环境没有修改配置，实际使用的是 Agent 时间 Tool 的
JioNLP 确定性解析路径，解释来源在 Tool 结果投影后记录为 `jionlp`。无法解析的时间表达由 Tool 返回
`unsupported`，再由 Agent 调用 `clarify`，不会自动改用默认日期。

在贯穿示例中，固定基准时间是 `2026-08-12 10:00:00+08:00`。按照当前“最近 N 天包含基准日期”的口径：

| 时间内容 | 示例结果 |
| --- | --- |
| 用户原文 | `最近 7 天` |
| 开始日期 | `2026-08-06` |
| 结束边界 | `2026-08-13`，不包含该日期 |
| 可信范围 | `[2026-08-06, 2026-08-13)` |

如果用户第二天才回复维度澄清，系统仍然使用 Run 中原来保存的 `2026-08-12` 作为基准日期，不会把范围移动一天。

### 6. 模型生成查询组织方式，服务端校验结果

查询组织方式属于用户语义的一部分，由意图识别模型直接生成，而不是由服务端再次读取问题文本并重新判断。模型必须完整输出：

- `select_mode`：明细查询或聚合查询
- `needs_group_by`：是否需要分组
- `needs_order_by`：是否需要排序
- `order_direction`：升序或降序
- `limit`：明确表达的数量限制
- `time_grain`：明确表达的日、周、月、季度或年粒度

例如，“销售额最高的 5 个城市”应由模型识别为聚合、按维度分组、降序、限制 5 条；“最近 7 天每天的销售趋势”应由模型识别为按天分组。模型不能因为排名分析通常需要 TopN 就自行补一个默认数量，也不能在用户没有表达“每天”“按月”等粒度时自行补时间粒度。

服务端不再使用“最高”“最低”“前 N”“每天”等自然语言硬编码规则覆盖模型结果。服务端只做以下处理：

1. 使用严格数据模型校验字段是否齐全、类型是否正确、枚举值和数值范围是否合法。
2. 校验意图、维度槽位和 `query_shape` 是否相互一致。
3. 根据已经确认的结果派生 `required_slot_types`，供后续流程判断必须具备哪些信息。这个字段是机械派生字段，不包含新的语言理解。

需要校验的一致性包括：

- 明细意图必须使用明细查询方式，其他意图不能错误标记为明细查询。
- 声明需要排序时必须给出排序方向；没有排序时不能携带排序方向或数量限制。
- 声明时间粒度时必须同时声明分组。
- 已识别出分组维度时，必须声明需要分组。
- 排名分析必须有排名维度、排序方式和明确的数量限制。
- 趋势分析必须有时间范围或时间粒度。

贯穿示例在用户澄清之前的结果是：

| 内容 | 示例结果 |
| --- | --- |
| 查询方式 | 聚合查询 |
| `select_mode` | `aggregate` |
| `needs_group_by` | `false` |
| `needs_order_by` | `false` |
| `limit` | `null` |
| 门店维度 | 暂时不能确定，因为角色为 `ambiguous` |
| 服务端派生的必需槽位 | 指标、维度、时间维度 |

用户选择“按门店分组查看”后，服务端只应用这项结构化用户选择：把“门店”改为 `group_by`，并把 `needs_group_by` 同步为 `true`。这不是服务端重新猜测问题，而是把用户明确确认的结果写回已有结构。服务端不会因为示例中出现“最近 7 天”就自动改成趋势查询，因为用户没有表达“每天”“按天”或“走势”。

### 7. 执行确定性校验

问题理解结果生成后，会执行一组不调用模型的确定性校验，检查：

- 问题重写是否仍然缺少上下文
- 非明细查询是否缺少指标
- 是否存在意图冲突
- 时间范围字段是否包含原始表达；默认 Agent 路径的绝对化由 ReAct 时间 Tool 完成
- 维度用途是否明确
- 筛选维度是否缺少具体值
- 维度筛选值是否被错误识别为时间表达
- 查询方式与意图、维度、排序、数量限制和时间粒度是否一致

如果存在问题，校验结果会标记为 `clarification_required`，同时记录所有原因和需要澄清的槽位。

贯穿示例第一次校验时，指标和时间都已明确，但“门店”的用途不明确，因此主要校验结果为：

| 字段 | 示例结果 |
| --- | --- |
| `validation.status` | `clarification_required` |
| `reason_codes` | 包含 `dimension_role_ambiguous` |
| `clarification_slots` | 包含 `dimension` |

校验只报告问题，不会自行把“门店”改成分组或筛选。

### 8. 问题理解阶段的前置澄清

当前问题理解阶段能够直接构造两类前置澄清：

- 维度用于分组还是筛选不明确
- 维度已经确定用于筛选，但缺少具体筛选值

时间原始表达不再在这里直接解析。Agent 进入 ReAct 后可并发调用 `parse_time_range` 和
`search_semantic_assets`；只有时间 Tool 返回 `unsupported`，Agent 才调用 `clarify`。
如果语义检索同时产生指标歧义，系统先展示指标卡片，用户回答后再展示时间卡片。

例如系统识别到“门店”的用途不明确时，会提供：

- 按门店分组查看
- 筛选某个具体门店
- 不使用门店维度，查看汇总结果

如果问题理解阶段需要澄清，系统会在语义资产检索之前挂起 Run；如果澄清由 Agent Tool 产生，则会在语义检索和时间解析结果投影之后挂起 Run。两种路径都会把 Run 和问答记录设置为 `waiting_user`，并保存问题、选项和恢复目标。

澄清次数受预算限制，默认最多两次，防止无限追问。

贯穿示例会在进入语义资产检索之前向用户提问：

> 请确认“门店”在本次查询中的使用方式。

系统提供三个结构化选项：

- 按门店分组查看
- 筛选某个具体门店
- 不使用门店维度，查看汇总结果

用户选择“按门店分组查看”后，系统保存的恢复目标是：操作 `set_dimension_role`，目标槽位为“门店”。

### 9. 保存问题理解结果并进入 ReAct

问题理解完成后，系统会保存：

- 用户原始问题
- 重写后的问题
- 完整问题理解结果
- 消息快照
- 模型用量和预算
- 时间旁路观察结果（如果启用）

同时发布 `question-understood` 事件，事件中包含：

- 消息类型
- 重写后的问题
- 意图类型
- 置信度
- 校验结果

如果不需要前置澄清，Agent 使用重写后的问题和结构化理解结果进入 ReAct 循环。

贯穿示例第一次执行到这里时，因为需要确认“门店”的用途，所以保存快照后进入 `waiting_user`。没有前置澄清时，Agent 进入 ReAct，首轮按依赖关系并发执行时间解析和语义检索。

## 二、用户澄清后如何恢复

用户回答澄清问题后，系统不会重新执行完整的问题重写、意图识别和维度识别。

恢复过程是：

1. 恢复挂起前保存的预算、消息和问题理解结果。
2. 校验本次回复对应的恢复类型和目标槽位。
3. 只更新用户本次确认的维度角色、筛选值或时间范围。
4. 把用户确认的结构化选择同步到对应槽位和查询组织方式。
5. 再次执行确定性校验。
6. 重新构造固定系统提示和动态上下文，把 Run 和问答记录恢复为 `running`。
7. 如果队列中仍有其他澄清，再次挂起并展示下一张卡片；否则继续进入 ReAct。

这种方式可以保留挂起前已经确认的理解结果，避免用户只回答一个问题时，其他意图因为重新调用模型而发生变化。

贯穿示例中，用户回复“按门店分组查看”后的变化如下：

| 内容 | 澄清前 | 澄清后 |
| --- | --- | --- |
| 重写问题 | 查询最近 7 天门店的销售额 | 保持不变 |
| 指标 | 销售额 | 保持不变 |
| 时间范围 | `[2026-08-06, 2026-08-13)` | 保持不变 |
| 门店角色 | `ambiguous` | `group_by` |
| 校验状态 | `clarification_required` | `valid` |
| Run 状态 | `waiting_user` | `running` |

恢复过程不会重新调用三个问题理解模型，只更新“门店”槽位和与其直接对应的 `needs_group_by`，重新执行确定性校验，然后继续 ReAct。

## 三、当前实现的亮点

### 1. 将复杂理解任务拆成三个独立模型任务

问题重写先执行；意图识别和维度识别只依赖重写结果，并行执行。意图任务不输出具体维度字段，维度任务也不接收意图任务的指标和时间结果。两个结果在服务端合并并执行跨任务一致性校验，减少串行错误传递并降低调用耗时。

### 2. 模型负责语义生成，服务端负责约束和校验

模型负责生成意图、指标、维度用途和完整查询组织方式。服务端负责严格格式校验、跨字段语义一致性校验、维度标准名称、时间范围计算以及必需槽位派生。服务端不会用自然语言关键词规则静默覆盖模型生成的排序方向、TopN 或时间粒度。

### 3. 使用严格的数据契约约束模型输出

每个任务都要求模型只返回 JSON，并使用严格的 Pydantic 模型校验：

- 禁止额外字段
- 限制枚举值
- 限制置信度范围
- 校验维度提及和维度槽位一一对应

首次输出不合法时，系统会把具体字段位置和校验错误反馈给模型，允许修复一次。第二次仍不合法时明确失败，不使用静默降级结果继续执行。

格式正确不等于语义正确，因此结果合并后还会继续检查意图、维度和查询组织方式之间的关系。例如，模型输出了 `limit=5` 却声明不需要排序，或者已经识别了分组维度却声明不需要分组，都会被记录为不一致结果，而不是由服务端猜一个值覆盖过去。

### 4. 使用典型示例稳定模型输出

三个模型提示词除字段契约和必要规则外，分别提供少量完整输入输出示例：

- 问题重写：独立新问题、只替换时间的追问、缺少引用上下文的追问。
- 意图识别：TopN 排名、按天趋势、普通指标查询。
- 维度识别：排名对象、明确筛选值、用途不明确的维度。

示例直接展示输入 JSON 和预期输出 JSON，帮助模型学习任务边界。意图示例不输出具体维度，维度示例不依赖意图模型结果，保持两个并行任务相互独立。

### 5. 维度理解和当前语义数据集结合

模型识别自然语言，服务端使用当前数据集的维度名称、别名和值进行规范化。这比完全依赖模型猜测维度名称更稳定，同时又没有提前绑定数据库字段或表。

### 6. 在检索和 SQL 之前处理高风险歧义

对于已经支持的时间和维度歧义，系统先向用户确认，再进入语义资产检索。这样可以避免错误的筛选值或分组方式继续影响语义检索、查询计划和 SQL。

### 7. 澄清恢复只修改目标槽位

用户回复后不重新运行完整理解流程，只修改对应槽位并重新校验，避免已经确认的语义发生变化。

### 8. 固定时间上下文

相对时间使用 Run 创建时保存的时间上下文进行解释，保证重试、澄清恢复和回放结果一致。

### 9. 问题理解结果是后续流程的统一依据

原始问题、重写问题、意图、指标、维度、时间、查询形态和校验结果被统一保存在 `QuestionUnderstandingOutput` 中，后续 Agent 和工具读取同一份结果，减少不同阶段分别理解用户问题造成的不一致。

贯穿示例集中体现了这些亮点：模型先把追问补全并识别“销售额”“最近 7 天”“门店”，服务端再固定绝对日期、规范化维度并发现角色歧义。用户确认后只修改“门店”槽位，其他已经确认的内容保持不变。

## 四、当前需要注意的限制

当前确定性校验能够识别的问题，比前置澄清能够直接处理的问题更多。

例如，系统可以识别：

- 意图未知
- 缺少指标
- 上下文不完整
- 意图冲突
- 维度值存在歧义

但当前前置澄清只直接处理：

- 模型权威时间计划需要确认
- 维度角色不明确
- 维度筛选值缺失

因此，`validation.status` 为 `clarification_required`，不一定表示问题理解阶段会立即挂起。没有映射为前置澄清的问题会继续进入 ReAct，由 Agent 判断后续是否需要调用澄清工具。

另外，问题重写只使用最近一次成功执行的问题，不使用完整多轮历史。完整的最近问答摘要是在问题理解完成后加入 Agent 的动态上下文消息中的，不再拼接到固定系统提示中。

贯穿示例能够正确继承“销售额”，前提是它确实指向最近一次成功问题“查询本月销售额”。如果用户说“那最近 7 天门店的呢？”实际想引用上上轮的另一个指标，当前重写输入无法可靠判断该引用关系，可能需要用户重新明确指标。这正是只使用最近一次成功问题带来的限制。
