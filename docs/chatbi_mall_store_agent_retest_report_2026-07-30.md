# ChatBI“商城店铺主题”Agent 真实测试报告（问题理解迁移后复测）

## 1. 测试结论

本轮使用当前运行中的 Chat Agent、真实模型、真实语义层和真实商城数据，设计了 10 个覆盖不同分析层面的测试问题。所有对象筛选均使用真实具体 ID；出现结构化澄清的问题，其每个选项均建立独立分支并实际选择。

总体结论：具体 ID 的问题理解能力已经明显改善，但当前版本仍不能稳定通过语义层完成问数。

- 共执行 `20` 次真实 Agent Run，包括主问题、全部选项分支和两次为确保选项实际提交而进行的稳定性重跑。
- 10 个主问题中，直接得到正确答案的有 `4/10`：Q1、Q2、Q5、Q6。
- Q4 只有选择“不使用商品ID维度”后得到正确答案，但该选项与原问题的排名意图冲突，因此不计为业务通过。
- 问题理解结构阶段首次通过 `9/10`，只有 Q7 因维度输出契约不一致失败。
- `compile_semantic_sql` 共调用 `21` 次，成功 `0` 次，拒绝 `19` 次，参数错误 `2` 次。
- SQL 执行共调用 `6` 次，成功 `5` 次，超时 `1` 次。
- 成功回答全部依赖 Agent 手写物理表 SQL，不是标准语义编译结果。
- “客户数”产生的 5 个指标选项均已实际选择；5 个分支最终全部失败。

因此，本轮标准语义全链路通过率仍为 **0%**。当前最主要的问题已经不是“店铺100011能否被识别”，而是具体值进入检索后被判定为未绑定，导致语义决策一直是 `partial`，编译器随后统一拒绝执行。

### 4.1 Q1：单指标具体店铺 ID

问题理解结果正确：

```json
{
  "metric_mentions": ["总下单客户数"],
  "dimension_slots": [
    {
      "name": "档口ID",
      "role": "filter",
      "value": "100011"
    }
  ],
  "time_range": {
    "start": "2026-06-30",
    "end_exclusive": "2026-07-01"
  }
}
```

检索已经选中：

- 指标 `274`：总下单客户数。
- 维度 `278`：档口ID。
- 时间维度 `276`：统计日期。

但具体值子查询 `value:1` 返回：

```json
{
  "status": "missed",
  "reason_codes": ["NO_CANDIDATE_ABOVE_HARD_FILTERS"]
}
```

整个语义决策因此为 `partial`，`compile_semantic_sql` 返回 `semantic_decision_not_executable`。Agent 最终手写 SQL 查询物理表，得到正确结果 `3`。

### 4.2 Q2：多指标

三个指标资产和档口维度都被正确选中，但具体 ID 值仍然形成 `missed value slot`。Agent 连续进行了 3 次语义编译，全部被拒绝，然后改为物理表 SQL。

数据库结果：

```json
{
  "gmv_sale": 8364.36,
  "gmv_booking": 0.0,
  "gmv_total": 8364.36
}
```

### 4.3 Q3 与 Q8：时间范围和直接回答

两个问题都包含常见中文范围：

```text

```

```json

  "raw": "2026年6月1日至30日"
```

进入 Agent 第一步后，模型没有调用任何工具，而是尝试直接回答。运行时守卫正确阻止了没有查询结果的回答，并返回：

```text

```

这说明守卫本身有效，问题在于时间 AST 不可执行后没有确定性的修复或查询计划。

## 8. 公共问题归纳

### P0：具体 ID 值被错误地要求参与语义候选检索

店铺 `100011` 已经明确属于档口ID筛选值，不需要再检索一个“100011语义资产”。当前检索仍生成必需的 `value` 子查询；由于索引中没有该值的候选文档，决策被标记为 `partial`。

这是 `semantic_decision_not_executable` 的主要公共原因，影响单指标、多指标、对比查询以及全部客户数澄清分支。

### P0：澄清结果没有形成不可重新解释的执行事实

用户选择指标后，指标槽位已经记录 `USER_CLARIFICATION_SELECTED`，但后续重复检索仍能重新打开歧义；明确的档口值也继续使决策保持 `partial`。澄清结果没有让执行决策收敛。

### P1：Agent 对不可执行理解缺少确定性处理

趋势、异常和部分澄清恢复场景中，Agent 在没有调用工具时尝试直接回答。运行时守卫正确拒绝，但系统没有在守卫前将 `unsupported time range`、缺失分组维度等状态转换为明确的修复或澄清动作。

### P1：问题理解仍存在三个边界问题

1. 排名问题中的输出对象“商品ID”没有确定性推导为 `group_by`。
2. 中文省略式日期范围“2026年6月1日至30日”无法归一化。
3. “近7天销量”“近30天销量”等完整指标名称可能被同时当成时间范围。

### P1：澄清后的问题理解与原问题出现双事实源

Q4 选择“忽略商品ID”后，结构化问题理解已经删除商品ID，但 Agent 仍根据原问题查询并返回商品 Top5。最终答案正确，却说明执行阶段没有严格使用问题理解输出作为唯一事实源。

### P2：失败调用会持续消耗预算

本轮出现：

- `compile_semantic_sql` 重复使用近似参数调用。
- `invalid_tool_args` 后继续尝试同类参数。
- 已选择指标后再次澄清。
- 手写 SQL 已验证但没有剩余步骤执行。

熔断和预算限制最终阻止了无限循环，但目前主要承担的是终止失败，而不是帮助流程收敛。

## 9. 最终评价

本轮迁移已经解决了此前最明显的具体 ID 识别问题：

- “店铺100011”可以稳定映射为 `档口ID=100011`。
- 字母数字商品 ID 可以进入筛选槽位。
- 单日时间可以生成正确半开区间。
- 客户数可以返回受控的 5 个真实语义指标选项。

但从真实 Chat Agent 全链路看，当前仍不具备稳定发布条件：

1. 明确 ID 值使语义决策保持 `partial`。
2. 标准语义编译成功率为 `0/21`。
3. 用户澄清不能保证后续执行收敛。
4. 趋势、异常、占比和多时间修饰指标仍不稳定。
5. 成功结果全部依赖手写物理 SQL。

下一阶段应优先解决“明确筛选值如何直接绑定到已选维度”以及“用户选择如何生成不可重新打开的语义决策”这两个公共问题，再测试 Agent 的规划与回答质量。
