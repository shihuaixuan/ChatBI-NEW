# ChatBI“商城店铺主题”维度值修复后 Agent 复测报告

## 1. 测试结论

本轮在“维度值不再参与语义资产检索”修改完成后，重新使用真实 Chat Agent、真实模型、真实语义层和真实商城数据执行测试。

测试包含 10 个不同分析层面的问题。所有筛选对象均使用真实具体 ID；出现结构化澄清时，每个选项都建立独立 Agent Run 并实际选择。正式测试共执行 `18` 次 Agent Run，另执行 `1` 次冒烟验证，并对 Q4 的无选项自由文本澄清进行了补充恢复测试。

本轮最重要的结果是：维度值检索问题已经修复。

- 共有 `12` 个 Run 进入语义绑定阶段，全部没有生成 `value:*` 子查询。
- 店铺 ID `100011`、商品 ID `P1000101001`、订单号 `USO202606300001` 均作为字面筛选值保留。
- `semantic_decision_not_executable` 出现次数为 `0`。
- `compile_semantic_sql` 正式测试共调用 `14` 次：成功 `12` 次，失败 `2` 次。
- 上一轮 `compile_semantic_sql` 调用 `21` 次、成功 `0` 次，本轮标准语义编译已经能够正常工作。
- Q10“客户数”的 `5` 个指标选项全部选择、全部语义编译成功、全部得到正确结果。

但是，整体 Chat Agent 仍未稳定：

- 10 个业务场景中，Q1、Q2、Q7、Q10 可以判定通过，即 `4/10`。
- Q1、Q2、Q7 无澄清直接完成；Q10 在完成必要的指标澄清后通过。
- Q3、Q8 仍无法识别“2026年6月1日至30日”。
- Q9 仍把指标名称中的“近7天、近30天”并入全局时间范围。
- Q4 仍无法确定排名问题中的商品ID应作为分组维度。
- Q5 把两个店铺 ID 合并为字符串并使用 `=`，生成了错误 SQL。
- Q6 把“是否超时”当作指标检索，而语义层中它是维度，导致语义决策为 `partial`。
- Q5 虽然已经生成正确的手写 SQL，但在执行前耗尽预算。

因此，本次修改解决了一个公共阻断问题，但也使其他问题更清楚地暴露出来。当前首要问题已经从“任意维度值导致语义决策不可执行”，转变为时间归一化、多值筛选表达、维度用途判断和 Agent 工具规划效率。

## 5. 维度值修复验证

### 5.1 Q1 的语义编译计划

Q1 的语义决策为 `resolved`，编译计划为：

```json
{
  "metric_asset_ids": [274],
  "dimension_asset_ids": [],
  "filters": [
    {
      "asset_id": 278,
      "operator": "=",
      "value": "100011"
    },
    {
      "asset_id": 276,
      "operator": "=",
      "value": {
        "kind": "absolute_range",
        "start": "2026-06-30",
        "end_exclusive": "2026-07-01",
        "timezone": "Asia/Shanghai"
      }
    }
  ]
}
```

检索计划只包含：

```text
metric:1
dimension:1
time_dimension:model:246
```

不再包含：

```text
value:1
```

编译生成的 SQL：

```sql
select
    sum(fct_stall_order_daily.order_customer_cnt_total)
        as order_customer_cnt_total
from fct_stall_order_daily fct_stall_order_daily
where fct_stall_order_daily.stall_id = '100011'
  and fct_stall_order_daily.stat_date >= '2026-06-30'
  and fct_stall_order_daily.stat_date < '2026-07-01'
limit 100
```

执行结果为 `3`，与数据库基准一致。

## 8. 其他问题详细分析

### 8.1 Q2：多指标标准语义路径通过

语义层一次选择三个指标：

```json
{
  "metric_asset_ids": [269, 270, 271],
  "filters": [
    {"asset_id": 278, "operator": "=", "value": "100011"},
    {"asset_id": 276, "operator": "=", "value": "2026-06-30"}
  ]
}
```

执行结果：

```json
{
  "gmv_sale": 8364.36,
  "gmv_booking": 0.0,
  "gmv_total": 8364.36
}
```

这是标准语义编译结果，不再依赖 Agent 手写 SQL。

### 8.2 Q3 与 Q8：日期范围仍不支持

两个问题中的日期表达均为：

```text
2026年6月1日至30日
```

问题理解结果：

```json
{
  "validation": {
    "status": "clarification_required",
    "reason_codes": ["time_range_unsupported"],
    "clarification_slots": ["time_range"]
  }
}
```

但是系统没有生成时间澄清卡，而是进入 Agent 推理。模型随后尝试直接回答，被“必须存在成功查询结果”的守卫拦截。

因此这里存在两个问题：

1. 常见中文同月日期范围没有被时间归一化器支持。
2. `clarification_required` 没有稳定转换为前置澄清，仍然进入了 Agent 工具规划。

### 8.3 Q5：多值筛选被错误编码为单值

问题理解将两个店铺写成：

```json
{
  "name": "档口ID",
  "role": "filter",
  "value": "100011,100012",
  "value_status": "provided"
}
```

编译计划继续使用：

```json
{
  "asset_id": 278,
  "operator": "=",
  "value": "100011,100012"
}
```

最终语义 SQL 为：

```sql
where stall_id = '100011,100012'
```

该 SQL 可以编译，但业务语义错误。正确表达应为：

```json
{
  "asset_id": 278,
  "operator": "in",
  "value": ["100011", "100012"]
}
```

Agent 后续识别到需要对比，生成并校验了正确手写 SQL：

```sql
SELECT stall_id, SUM(gmv_total) AS total_gmv
FROM fct_stall_order_daily
WHERE stat_date = '2026-06-30'
  AND stall_id IN (100011, 100012)
GROUP BY stall_id
ORDER BY total_gmv DESC
LIMIT 100
```

但预算在 `execute_sql` 前耗尽，因此最终没有答案。

### 8.4 Q6：“是否超时”的资产类型错误

问题理解正确保留：

```json
{
  "dimension_slots": [
    {"name": "档口ID", "value": "100011"},
    {"name": "未发订单号", "value": "USO202606300001"}
  ],
  "metric_mentions": ["订单金额", "未发件数", "是否超时"]
}
```

订单金额和未发件数成功绑定到指标资产 `276`、`279`，两个 ID 也都正确成为过滤条件。但是“是否超时”在当前语义层是维度，问题理解却把它作为指标检索，导致第三个指标槽位：

```json
{
  "subquery_id": "metric:3",
  "status": "missed",
  "reason_codes": ["TOP1_BELOW_ABSOLUTE_THRESHOLD"]
}
```

最终语义决策为 `partial`。这次失败与具体 ID 无关，而是明细问题中“需要展示的维度字段”被当作指标。

### 8.5 Q7：占比问题通过，但 time_bucket 参数不稳定

Q7 正确绑定销售类GMV和总GMV，编译并执行得到：

```json
{
  "gmv_sale": 8364.36,
  "gmv_total": 8364.36
}
```

最终计算占比 `100%`，结果正确。

但第一次编译时模型额外传入：

```json
{
  "time_bucket": {"type": "day"}
}
```

编译器返回：

```text
SEMANTIC_SQL_TIME_GRAIN_UNSUPPORTED
```

第二次去掉 `time_bucket` 后成功。单日汇总问题不需要时间分桶，工具规划仍存在无效试错。

### 8.6 Q9：指标名称再次污染时间范围

问题中的三个指标是：

```text
当前库存件数
近7天销量
近30天销量
```

其中“近7天销量”和“近30天销量”是语义层定义的完整指标名称，不应成为全局时间筛选。但本轮问题理解仍返回 `time_range_unsupported`，导致整个问题在进入工具前失败。

该问题与上一轮一致，说明问题理解阶段尚未建立“先识别完整指标名称，再从剩余文本抽取时间”的稳定边界。

## 11. 当前问题优先级

### P0：多值筛选必须形成明确契约

当前 `100011,100012 + operator="="` 会生成可执行但业务错误的 SQL。问题理解输出、多值标准化和 SQL 编译之间需要统一为：

```json
{
  "operator": "in",
  "value": ["100011", "100012"]
}
```

不能依赖 Agent 在编译后发现错误再手写 SQL。

### P0：时间范围归一化

必须支持同月省略年份和月份的常见表达，例如：

```text
2026年6月1日至30日
```

并保证 `clarification_required` 一定在进入 Agent 前产生可回答的时间澄清。

### P1：指标名称和时间表达边界

“近7天销量”“近30天销量”应优先作为完整指标名称，不能再次进入全局时间范围。

### P1：排名问题中的维度用途

“最高的5个商品ID”已经确定商品ID是排名和展示维度，不应再次询问分组、筛选或忽略。

### P1：明细展示字段不能全部作为指标

“是否超时”在当前语义层是维度。明细查询需要区分：

- 聚合指标；
- 明细展示维度；
- 筛选维度及字面值。

### P2：减少重复检索和无效编译

Q1、Q2 在语义资产已命中后仍调用物理 Schema 或重复检索；Q5 连续编译 5 次；Q7 尝试了无效 `time_bucket`。这些步骤增加延迟和 Token 消耗，并可能导致预算在真正执行前耗尽。
