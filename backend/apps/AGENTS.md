# 领域模块通用架构规则

## 1. 适用范围

本规则适用于 `backend/apps/` 下所有业务领域的新建、拆分和迁移。

`apps/<domain>/` 本身代表一个业务领域。领域内部按职责分层，不再机械增加另一套同义的领域目录。目录必须由实际职责产生，禁止为了形式完整而创建空层。

推荐的基础结构如下：

```text
apps/<domain>/
├── api/                   # 存在接口入口时建立
├── services/              # 业务流程和业务规则
├── repository/            # 仓储接口及其实现
│   └── <technology>/      # 按实际持久化或外部技术建立
├── models/
│   ├── orm/               # 持久化对象
│   └── dto/               # 数据传输对象
├── utils/                 # 通用纯辅助能力
├── errors.py              # 领域公共错误
└── __init__.py
```

领域没有某类职责时，可以省略对应目录。存在较多同类能力时，可以在所属层下继续按职责建立子目录，但不得形成重复层级，例如 `services/services/`。

## 2. 分层职责

### 2.1 `api/`

- 负责接口定义、参数接收、身份上下文和响应转换。
- 负责组装 Service 及其依赖，或调用统一的依赖组装入口。
- 负责将领域错误转换为接口层错误。
- 不承载业务规则、持久化查询和事务逻辑。
- 不将接口框架对象传入 Service。

### 2.2 `services/`

- 负责业务流程、业务校验、权限判断和能力调用顺序。
- 依赖仓储接口，不依赖仓储的具体技术实现。
- 不直接使用数据库会话、持久化框架客户端或查询语句。
- 不处理接口状态码和接口框架异常。
- 业务主流程应保持可读，不为了拆分而建立大量只调用一次的方法或类。

### 2.3 `repository/`

- 根目录存放面向 Service 的仓储接口。
- 技术子目录存放数据库、搜索引擎、文件系统或外部服务的具体实现。
- 仓储接口按业务需要定义，不直接暴露底层查询方式。
- 具体实现负责查询、写入、关系同步和持久化事务。
- 仓储不得依赖 Service 或 API。
- 禁止静默忽略数据访问错误，禁止用无依据的默认数据掩盖失败。

一次业务写入所要求的关联更新必须保持原子性。如果一个操作确实需要多个仓储共享事务，应建立明确的事务协调边界，不得将数据库会话直接交给 Service。

### 2.4 `models/orm/`

- 存放与持久化结构映射的对象。
- 按业务资源拆分，避免一个文件承载整个领域的全部模型。
- 只描述持久化结构、字段约束、索引和必要的默认值。
- 不包含接口逻辑、业务流程和查询流程。
- ORM 对象是持久化对象，不使用 `Entity` 命名以免与严格 DDD 领域实体混淆。

### 2.5 `models/dto/`

- 存放接口入参、业务流转参数、查询条件和结果数据结构。
- DTO 不映射数据库表，不持有外部连接，不执行持久化。
- 同一数据契约只定义一次，由实际调用方共享。
- `__init__.py` 只做稳定导出，不放具体模型定义。

### 2.6 `utils/`

- 只放无状态、无外部副作用且存在实际复用的辅助函数。
- 不放业务流程、业务规则、权限判断、数据库访问或接口调用。
- 仅服务于一个业务流程的代码应保留在该流程所属位置，不能为了缩短文件而移入 `utils/`。

### 2.7 `errors.py`

- 定义领域公共错误基类和含义明确的错误类型。
- 错误表达业务失败原因，不绑定接口状态码。
- 未知异常不得被转换为成功结果或模糊错误。

## 3. 依赖方向

允许的主要依赖方向：

```text
api -> services
api -> repository/<implementation>   # 仅用于依赖组装
api -> models/dto

services -> repository               # 只依赖仓储接口
services -> models
services -> errors
services -> utils

repository/<implementation> -> repository
repository/<implementation> -> models/orm
repository/<implementation> -> 外部技术组件

repository -> models
```

禁止以下反向依赖：

```text
repository -> services
models -> services
models -> repository
services -> api
services -> repository/<implementation>
```

不得通过函数内部导入或延迟导入掩盖循环依赖。出现循环依赖时，应重新确认职责归属或抽取稳定的数据契约。

## 4. 跨领域规则

- 一个领域不得直接依赖另一个领域的具体仓储实现。
- 跨领域调用应通过公开 Service、稳定协议或明确的数据契约完成。
- 外部领域的数据结构需要转换时，在调用边界完成转换，不能把对方的内部模型扩散到本领域各层。
- 共享代码只有在多个领域存在稳定且一致的复用需求后，才允许移动到公共目录。
- 名称相似不代表职责相同，抽取共享能力前必须确认业务语义和变化原因一致。
- 每项业务能力只能保留一个权威实现，禁止长期并存多套同类链路。

## 5. 命名规则

- 领域、目录、文件、类和方法名称必须表达业务职责，禁止使用无法说明用途的宽泛名称。
- 文件和目录统一使用 `snake_case`，类使用 `PascalCase`，函数和变量使用 `snake_case`。
- Service、Repository、DTO 和错误类型的名称应包含其负责的资源或行为。
- 接口与具体实现应使用同一业务名称，具体实现额外体现所用技术或数据来源。
- `Builder` 只表示复杂对象组装，`Matcher` 只表示匹配选择，`Mapper` 只表示明确的结构转换。
- `Manager`、`Helper`、`Common` 等模糊名称原则上禁止使用，除非能够证明其职责单一且名称不会造成误解。
- 禁止使用单个 `service.py`、`models.py`、`schemas.py` 或 `api.py` 承载整个领域；应按资源或能力拆分。
- 历史品牌名、废弃方案名和技术实现名不得继续出现在无关的业务命名中。

## 6. 逻辑与事务规则

- 同一个业务不变量只能有一个权威实现位置。
- Service 决定业务是否允许执行以及执行顺序。
- Repository 负责数据读取、持久化方式和单次持久化操作的原子性。
- 纯计算、转换和规则判断应与外部访问分离，便于独立测试。
- 数据库约束负责最终数据一致性，但不能替代必要的业务校验。
- 公共校验、权限、配置和错误映射必须有统一入口，禁止在多层重复实现。
- 不使用宽泛异常捕获吞掉错误，不使用静默回退掩盖配置、依赖或数据问题。

## 7. 迁移流程

1. 盘点领域边界，包括入口、业务能力、数据对象、外部依赖、调用方和测试。
2. 识别重复能力和废弃链路，确定唯一保留方案。
3. 统一领域内的资源、文件、类和接口命名。
4. 按实际职责建立目标目录，不提前创建无代码的层级。
5. 将持久化对象和数据传输对象分别迁入 `models/orm` 与 `models/dto`。
6. 根据 Service 的真实数据需求定义最小仓储接口。
7. 将查询、写入和事务迁入仓储具体实现。
8. 将业务流程和业务规则收敛到 Service，清除其具体技术依赖。
9. 在入口层完成依赖组装和错误转换。
10. 更新跨领域调用和测试，删除旧实现、旧入口与无效兼容代码。
11. 执行领域测试、主要调用方测试、静态检查和数据库迁移验证。

如迁移期间必须保留兼容入口，兼容入口只能转发到唯一实现，并且必须明确删除条件，不能继续承载独立业务逻辑。

## 8. 测试规则

- Service 测试使用仓储接口的 Fake 或 Mock，不创建真实数据库会话。
- Repository 测试覆盖数据范围、隔离条件、事务、关系同步和级联操作。
- API 测试覆盖接口契约、身份校验和错误转换。
- 纯业务规则和转换逻辑使用单元测试覆盖关键业务不变量。
- 跨领域调用保留必要的集成测试，防止公开契约被迁移破坏。
- 缺陷测试应覆盖问题产生机制，不能只固定某一个案例输入。

## 9. 迁移验收

领域迁移同时满足以下条件才算完成：

- 目录与实际职责一致，不存在空层、重复层和职责不明的目录。
- Service 不直接依赖数据库会话、持久化客户端或具体仓储实现。
- API 不包含查询、事务和重复业务规则。
- 仓储接口与具体实现分离，依赖可在入口处组装。
- ORM 与 DTO 已分离，领域模型不再集中在单个大型文件中。
- 跨领域调用不依赖对方的内部实现。
- 旧模块、旧导入路径、重复能力和无效兼容代码已删除。
- 没有新增循环依赖，也没有用延迟导入掩盖依赖问题。
- 领域测试、主要调用方测试、静态检查和数据库迁移检查通过。

## 10. 评审原则

- 先确认领域边界和业务不变量，再评审目录结构。
- 先消除重复能力，再考虑抽取公共能力。
- 以业务主流程可读为优先，不为了分层而过度拆分。
- 新增抽象必须能够形成稳定边界、减少真实重复或明显降低复杂度。
- 迁移不能只移动文件，必须同时修正错误依赖和重复职责。
